# backend-agent — 기억의 조각 API

**1주차 게이트: 텍스트만으로 3턴이 끝까지 돌고, 구간별 지연 숫자가 로그에 남는다.**

오디오는 붙이지 않는다. STT·TTS·WebSocket을 동시에 얹으면 안 될 때 어디서 깨졌는지 못 찾는다.

```powershell
pip install -r requirements.txt
python -m tests.test_flow                          # 23건 검증
uvicorn app.main:app --reload --port 8010
```

`http://127.0.0.1:8010/docs` 에서 API를 눌러볼 수 있다. 화면은 `frontend-client` 저장소에 있다.

    migrate.py            마이그레이션 적용 · 체크섬 · advisory lock

`machine.py`가 FastAPI도 asyncio도 import하지 않는 게 중요하다. 순수 파이썬이라야 전이를 전부 단위 테스트로 돌려볼 수 있고, 실시간 계층을 바꿔도 살아남는다.

## 핵심 설계 하나

T1이 만료되면 **T2와 질문 생성을 동시에 건다.**

```
T1 만료 (발화 확정)
   ├──▶ T2 카운트다운 시작 ────────────┐
   └──▶ 조각 저장 → 질문 생성 (비동기) ┘
                                      둘 다 참이어야 다음 질문이 나간다
```

순차로 짜면 T2가 끝난 뒤 질문 생성을 시작해 8 + 1.5 = 9.5초가 된다. 병렬로 걸면 처리 시간이 T2 안에 숨어 어르신은 지연을 못 느낀다.

```
턴 1 지연 3001ms  (저장 0 · 질문 201 · 전달 2800)
                            ↑           ↑
                  질문은 201ms에 준비    나머지는 T2를 기다린 시간
```

**예산은 T2 최솟값 3초(빠름 설정) 기준으로 잡는다.**

## 상태 전이

```
SPEAKING ──낭독 끝──▶ LISTENING ──T1 만료──▶ PROCESSING ──┬─▶ SPEAKING
                          ▲                              │   (질문 준비 AND T2 만료)
                          └──── 빈 전사 (턴 미소모) ──────┘
                                                         └─▶ CLOSED
```

| 규칙 | 왜 |
|---|---|
| T2는 **조각이 확정된 뒤** 센다 | 말을 멈춘 시각이 아니다 |
| 빈 전사는 **턴을 소모하지 않는다** | 무음이 반복돼도 턴이 소진되지 않는다 |
| 「다 말했어요」는 T1·T2를 **건너뛴다** | 지연이 그대로 드러나는 유일한 경로 |
| 대화 길이는 **정해두지 않았다** | 끝낼 때를 아는 것은 턴 수가 아니라 AI 다 (아래) |
| 턴 제한을 준 회차는 마지막에 질문을 **생성하지 않는다** | 내보내지 않을 질문에 비용을 쓰지 않는다 |
| 정의되지 않은 전이는 **409로 거부** | 조용히 무시하면 나중에 원인을 못 찾는다 |

### 몇 턴을 물을 것인가 — 세지 않기로 했다

`max_turn` 은 **0 이 기본이고, 0 은 「제한 없음」이다.**

처음에는 3턴으로 묶어 두었다. 흐름을 돌려보는 데는 그게 맞았지만, 실제로
어르신과 이야기를 해 보면 **세 번째 질문에서 끊는 근거가 아무것도 없다.**
어떤 기억은 두 마디로 끝나고 어떤 기억은 열 번을 물어야 열린다. 그걸 미리
숫자로 정해 두면 남는 건 「AI 가 기억을 더 들을 수 있었는데 카운터가 다 됐다」
뿐이다.

그래서 끝을 정하는 자리를 셋만 남겼다.

| 끝 | `closed_reason` | 누가 정하나 |
|---|---|---|
| 이야기가 마무리됐다 | `finish` | **AI** — `question.py` 가 `action: "close"` 를 고를 때 |
| 그만하겠다 | `abort` | 어르신 — 「중단」 버튼 |
| 여기까지만 받는다 | `max_turn` | 회차를 여는 쪽이 값을 줬을 때만 |

세 번째가 남아 있는 이유는 **시험 도구 때문**이다. `tools/replay.py` 는 녹음
파일 수만큼만 돌아야 하므로 `max_turn=len(files)` 를 주고 연다. 기계에서
도려내지 않고 0 을 특별한 값으로 둔 건 그래서다 — 묶고 싶은 쪽이 묶는다.

`turns_left` 는 제한이 없을 때 **-1** 이다. 0 을 쓸 수 없다. 그건 「이번이
마지막」이라는 뜻이고, 화면이 정반대로 읽는다.

#### 상한을 없앴더니 하한이 필요해졌다

상한을 걷어낸 첫 회차가 **턴 1에서 닫혔다.** 폰으로 시험하던 중이라 어르신
자리에서 나온 말이 질문에 대한 답이 아니었다.

```
질문   그 열차 안에서는 어떤 소리가 들렸나요?
대답   어떻게 지금 돼가고 있어?
AI     마무리 — "어르신이 대화의 흐름에서 벗어나 현재 상황을 물어보시어"
```

판단 자체는 말이 된다. 문제는 **그 문이 이제 유일한 출구**라는 것이다. 어르신이
「뭐라고?」 한 번 되물으시면 회차가 끝난다. 되묻는 건 흔한 일이고, 그때 할 일은
회차를 닫는 게 아니라 더 쉬운 말로 다시 여쭙는 것이다.

두 군데를 고쳤다.

| | 무엇 |
|---|---|
| 프롬프트 | 「대답이 질문과 어긋나거나, 못 알아들으신 것 같거나, 짧아도 close 가 아니다」를 규칙으로 명시 |
| 코드 | `MIN_TURN`(기본 3) 전에는 모델이 close 를 골라도 **따르지 않고** 다시 여쭙는다 |

코드 쪽을 남긴 이유는 프롬프트가 확률이기 때문이다. 온도 1.0 으로 도는 모델이
규칙을 한 번 흘리면 회차가 끝나고, 어르신에게는 그게 곧 끊김이다. `decision` 에
`overruled: "close"` 로 적어 두니 나중에 「모델이 몇 번 일찍 닫으려 했나」도
세어 볼 수 있다.

되돌려 본 결과 — 엉뚱한 대답 셋을 연달아 넣어도 회차가 살아 있다.

```
A 어떻게 지금 돼가고 있어?   → Q 열차 안에서 순애 씨 목소리가 어땠는지 기억나세요?
A 뭐라고? 잘 안 들려.        → Q 귀가 어두우셨죠, 순애 씨 손은 어떤 느낌이었나요?
A 이거 어떻게 하는 거야?     → Q 어르신, 순애 씨랑 열차 탔을 때 마음이 설레셨지요?
turn=3  closed_reason=None
```

그리고 제대로 된 대답 일곱 마디를 넣으면 일곱 턴을 돌고도 살아 있었다. 질문
생성은 847~1545ms (중앙 1011ms) 로 T2 예산 안이다.

## 개발은 localhost, https는 실기기 확인할 때만

**터널을 상시로 켜두지 않는다.** 손해가 더 크다.

브라우저는 `http://localhost`와 `127.0.0.1`을 **secure context** 로 취급한다. 그래서 https가 필요해 보이는 것들이 본인 컴퓨터에서는 그냥 된다.

| | localhost | LAN IP (http) | 터널 (https) |
|---|---|---|---|
| 마이크 권한 | ✓ | ✗ | ✓ |
| 구글 로그인 | ✓ | ✗ | ✓ |
| 서비스워커 · PWA | ✓ | ✗ | ✓ |

https가 실제로 필요한 건 **다른 기기에서 접속할 때**뿐이다.

### 평소 — 따로 띄운다

```powershell
# 이 창
uvicorn app.main:app --reload --port 8010
# 다른 창 (frontend-client)
npm run dev
```

Vite 개발 서버(5173)는 CORS에 이미 열려 있다. 핫리로드가 살아 있어 화면 작업이 빠르다.

### 실기기 확인 — 빌드해서 하나로 합친다

```powershell
cd ..\frontend-client
npm run deploy:backend        # 빌드 → ../backend-agent/web (낡은 번들은 지우고 복사)
cd ..\backend-agent
uvicorn app.main:app --port 8010
& "C:\Program Files\Tailscale\tailscale.exe" serve 8010
```

폰에서 `https://<기기이름>.<tailnet>.ts.net` 으로 들어간다. 주소는 `tailscale serve status` 가 알려준다.

**터널 하나면 되고, 같은 출처라 CORS 설정도 HMR 설정도 필요 없다.** https 라 마이크 권한도 확인할 수 있다.

#### `funnel` 이 아니라 `serve` 다

둘 다 https 를 주지만 노출 범위가 다르다.

| | 닿는 범위 | 인증서 |
|---|---|---|
| `serve` | **내 tailnet 안에서만** | 유효 (`*.ts.net`) |
| `funnel` | **공개 인터넷 전체** | 유효 |

확인할 폰은 이미 tailnet 안에 있다. 그러면 `serve` 로 충분하고, 로그인도 인증도 없는 1주차 서버를 공개 인터넷에 세워 둘 이유가 없다. `funnel` 은 tailnet 밖의 기기로 확인해야 할 때만 쓴다.

끝나면 `tailscale serve reset` 으로 내린다.

#### LAN IP 로 붙는 길은 왜 안 쓰나

같은 wifi 면 `http://<PC IP>:8010` 이 더 간단해 보인다. 두 가지가 걸린다.

- **http 는 secure context 가 아니다.** 위 표대로 마이크가 막힌다. 2주차에 이 길로 가면 `navigator.mediaDevices` 가 아예 `undefined` 로 나온다.
- 유선 인터페이스가 **Public 프로필**이라 인바운드가 기본으로 막힌다. 방화벽 규칙을 따로 열어야 하고, 그건 접속 환경이 바뀔 때마다 다시 걸린다.

`serve` 는 둘 다 해당이 없다.

#### 확인한 것 (1주차)

빌드본을 백엔드가 서빙하는 경로로 전 구간을 돌렸다.

| | |
|---|---|
| SPA · assets · `/api` 같은 출처 | 200 · CORS 불필요 |
| 없는 `/api` 경로 | 404 (index.html 을 돌려주지 않는다) |
| 3턴 완주 | `max_turn` 으로 CLOSED, 조각 4개 저장 |
| 질문 생성 | 875ms — T2 3초 **안에 숨었다** (전달 2136ms) |
| 타이머 격발 오차 | T1 +11ms · T2 +11ms (허용 ±200ms) |
| https 경유 1턴 | 정상, 인증서 유효 |

#### 여기서 한 번 걸렸다 — `TypeError: Load failed`

폰에서 버튼을 누르면 이것만 떴다. 서버는 멀쩡했고 curl 로는 전부 200 이었다.

`.env.local` 의 `VITE_API_BASE=http://localhost:8010` 이 **빌드본에 구워져** 있었다.
폰에서 `localhost` 는 폰 자신이라 요청이 갈 곳이 없고, https 페이지라 mixed content
로도 막힌다. 사파리는 그 둘을 구분해 주지 않고 `Load failed` 한 줄만 준다.

curl 로 API 를 직접 때리는 확인은 이걸 못 잡는다. **번들이 어디로 부르는지**를 따로
봐야 한다. 지금은 빌드 시점에 접히게 해 두었으니 이걸로 확인한다.

```powershell
Select-String 8010 ..\backend-agent\web\assets\*.js    # 아무것도 안 나와야 한다
```

**아이폰 사파리에서 확인 완료.** 화면이 뜨고 회차가 돈다. 마이크 권한은 오디오가 붙는 2주차에 같은 주소로 다시 본다 — https 라 확인할 수 있는 상태다.

### 터널로 상시 개발하면 걸리는 것

| | |
|---|---|
| 핫리로드 | HMR WebSocket 이 릴레이를 지나 느려지고, 별도 설정이 필요하다 |
| 대역폭 | 새로고침마다 번들 전체가 릴레이를 지난다 (`funnel` 은 조절 불가한 제한까지 있다) |
| **지연 측정** | **터널 왕복이 섞여 FR-AD-314 숫자가 오염된다** |
| 팀원 URL | 각자 기기 이름으로 만들어져 origin 이 6개가 된다 (CORS · OAuth 등록도 그만큼) |
| 유지 | Ctrl+C 하거나 컴퓨터가 자면 끊긴다 |

세 번째가 제일 중요하다. **NFR-PF-001 판정은 반드시 localhost 에서 잰다.** 터널을 낀 숫자는 참고용이고, 우리 코드가 느린 건지 터널이 느린 건지 가릴 수 없다.

### 이번 주에 터널이 꼭 필요한 것

**미결 #6 (지원 브라우저·기기) 실기기 확인** 하나뿐이다. 아이폰 사파리와 안드로이드 크롬에서 마이크 권한이 실제로 뜨는지 보는 작업이다. 나머지는 전부 localhost 로 한다.

```
평소 화면·로직 개발     localhost:5173 + localhost:8010
지연 측정 (KPI)         localhost 만. 터널 금지
폰에서 마이크 확인      빌드 → 백엔드 서빙 → 터널 하나
```

## 질문 생성 (Gemini)

`question.py` 의 `gemini_question` 이 `controller.QuestionFn` 자리에 들어간다.
꽂는 곳은 `main.py` 의 `create_session` 한 줄이다 — **SessionController 의 기본값은
`fixed_questions` 로 두었다.** 그래야 `tests/test_flow.py` 가 네트워크도 키도 없이 돈다.

| | |
|---|---|
| 모델 | `gemini-3.5-flash-lite` (저지연·저비용) |
| 예산 | **T2 최솟값 3초.** `GEMINI_TIMEOUT=2.5` 로 그보다 짧게 끊는다 |
| thinking | `MINIMAL`. 오래 생각할수록 어르신이 기다린다 |
| 실측 | 예열 후 934ms · 1210ms (「다 말했어요」 경로 — 지연이 숨을 곳이 없는 경로다) |

### 실패는 회차를 끝내지 않는다

`controller._make_question` 은 `None` 을 받으면 CLOSED 로 간다. 그건 **「AI 가 그만
물어도 되겠다고 판단했다」** 는 뜻이어야지, 네트워크가 한 번 끊겼다는 뜻이면 안 된다.

그래서 오류·타임아웃은 `question.py` 안에서 삼키고 고정 질문으로 물러선다.
`None` 은 모델이 `{"action":"close"}` 를 돌려줬을 때만 나간다 (FR-IV-006).

키가 아예 없으면 고정 질문으로 돈다. 프론트 작업이 키 발급을 기다리지 않아도 된다.

### 기동 시 예열한다

첫 호출이 2864ms, 이후가 ~950ms 였다. 차이는 질문 생성이 아니라 `genai.Client()`
생성과 첫 TLS 연결이고, 둘 다 `wait_for` **바깥**이라 타임아웃으로 막히지도 않는다.
안 데워 두면 **첫 어르신이 그 비용을 전부 낸다.**

`main.py` 의 lifespan 이 `warmup()` 을 던져 둔다. 기다리지는 않는다 — 예열은
최적화일 뿐이라 서버 기동을 막을 이유가 없다.

## 전사 (Azure Fast Transcription)

`stt.py` 가 오디오 한 덩어리를 글로 옮긴다. `question.py` 와 같은 모양이라
FSM 도 타이머도 이 파일의 존재를 모르고, `controller.stt_fn` 을 바꾸면 갈아 끼워진다.

### whisper-1 과 재보고 골랐다

각 10회씩, 같은 PC·같은 음성으로.

| 음성 14.6초 | 중앙값 | p90 | 편차 |
|---|---|---|---|
| whisper-1 | 1927ms | 2236ms | 819~2331 (2.8배) |
| **Azure** | **897ms** | **921ms** | 868~1046 (1.2배) |

중앙값이 두 배 빠른 것보다 **편차가 붙어 있는 게 더 중요했다.** 타이머 예산으로
도는 설계에서는 p90 이 설계를 정한다.

    T1 만료 뒤 전사 + 질문 생성  (T2 빠름 = 3.0초)
      whisper-1   p90 2236 + 875 = 3.1초   넘친다
      Azure       p90  921 + 875 = 1.8초   들어간다

whisper-1 이었다면 침묵이 시작되는 순간 전사를 미리 쏘고 어르신이 말을 이으면
취소하는 **투기적 호출**을 만들어야 했다. 취소 경로, 버려지는 호출, 그만큼의 복잡도.
Azure 는 그게 통째로 필요 없다.

정확도는 120자 기준 글자 오류율로 whisper 4.2% · whisper+씨앗 0.8% · Azure 1.7%
였다. Azure 가 지명·인명을 맞히고 조사·어미에서 틀리는 쪽이라 회고록에는 덜 아프다.

**이 수치는 TTS 로 만든 깨끗한 음성 기준이다.** 실제 녹음으로 다시 쟀고, 결과는
아래에 있다 — 정확도 순위가 뒤집혔다. 바꾸려면 `stt_fn` 하나다.

### 실제 목소리로 다시 쟀다 — 순위가 더 벌어졌다

위 수치는 TTS 로 만든 깨끗한 음성 기준이었다. 실제 녹음(16kHz 모노, 10초 안팎,
같은 문장 세 번)으로 다시 쟀더니 **Azure 쪽으로 더 벌어졌다.**

| | 지연 | 전사 |
|---|---|---|
| Azure | **719 · 545 · 544ms** | 큰형이 … 영등포역까지 마중을 나왔어 … 봉천동 |
| whisper-1 | 2600 · 1898 · 1894ms | 큰 양이 … 영돈포역까지 마중 올라왔어 … 봉천동 |

whisper 는 세 번 모두 「마중을 나왔어」를 「마중 올라왔어」로 바꿨고, 「큰형이」를
「큰 양이」로, 「영등포역」을 「영돈포역」으로 놓쳤다. **TTS 음성에서는 whisper 가
앞섰는데 실제 목소리에서 뒤집혔다.** 합성음은 발음이 고르고 잡음이 없어서 whisper
쪽에 유리했던 것으로 보인다.

지연도 3~4배로 벌어졌다. 고른 목소리가 아니면 whisper 가 더 오래 생각한다.

### tools/replay.py — 마이크 없이 오디오 경로를 돌린다

녹음 파일을 실제 회차처럼 흘려보낸다.

```powershell
python tools/replay.py                      # tools/recordings/turn*.wav 로 3턴
python tools/replay.py --base https://...   # 터널 너머의 서버로
python tools/replay.py --no-realtime        # 기다리지 않고 몰아서
```

**녹음 파일은 저장소에 올리지 않는다** (`.gitignore`). 사람 목소리라 그렇고, 저마다
자기 목소리로 받아 두는 편이 시험으로도 낫다. 16kHz 모노 wav 면 된다.

이 도구가 하는 일 중 중요한 건 **무음을 걸러내는 것**이다. 파일 전체를 밀어 넣으면
시험이 헐거워진다 — 실제 화면은 소리가 있는 청크만 올려야 하고, 무음까지 올리면
T1 이 영원히 리셋되어 발화가 확정되지 않는다. `_voiced()` 가 그 판정의 초안이고,
**프론트에 들어갈 무음 판정이 여기서 출발한다.**

wav 는 헤더에 데이터 길이가 박혀 있어 무음을 빼면 헤더를 다시 써야 한다.
브라우저가 쓸 webm/opus 는 패킷을 이어 붙여도 유효해서 이 손질이 필요 없다.

실제 녹음 3턴 결과:

    턴1  소리 7청크 · 무음 4청크 버림   말씀이 끝나고 6.1초 뒤 다음 질문
    턴2  소리 6청크 · 무음 4청크 버림   말씀이 끝나고 6.1초 뒤 다음 질문
    턴3  소리 7청크 · 무음 5청크 버림   말씀이 끝나고 3.7초 뒤 마무리

    턴1  전사 626 · 저장 12 · 질문 927 · 전달 1440   합계 3004ms
    턴2  전사 633 · 저장  1 · 질문 975 · 전달 1399   합계 3007ms
    타이머 격발 오차 최대 15ms · 평균 7ms

6.1초는 T1 3초 + T2 3초 그대로다. 합계가 T2 와 같다는 건 전사와 질문 생성이
침묵 안에 통째로 숨었다는 뜻이다. 마지막 턴이 3.7초인 것은 최대 턴에서 질문을
만들지 않고 닫기 때문이다 (FR-IV-006).

### T2 를 전사보다 먼저 건다

`_confirm()` 에서 순서가 중요하다.

    확정 ─┬─ T2 카운트다운 ───────────────────┐
          └─ 전사(921ms) → 질문 생성(875ms) ──┘  둘 다 끝나야 다음 질문

바꾸면 전사 시간이 T2 밖으로 새어 나와 어르신이 느끼는 틈이 그만큼 길어진다.
T2 는 **「말씀을 마치신 뒤의 사이」지 「서버가 일을 끝낸 뒤의 사이」가 아니다.**

실측(빠름 프리셋, 14.6초 음성):

    전사 1028 · 저장 13 · 질문 955 · 전달 1012   합계 3007ms

합계가 T2 3000ms 와 같다. 처리가 침묵 안에 통째로 숨었다는 뜻이다.
어르신이 느낀 틈은 T1 3초 + T2 3초 = 6.2초로, 텍스트였을 때와 같다.

### 빈 전사에 T1 을 다시 걸면 무한 루프다

**이번에 실제로 겪은 것이라 적어 둔다.**

빈 전사로 LISTENING 에 돌아갈 때 `reset_t1()` 을 무조건 부르면, 새 소리가 하나도
안 와도 3초 뒤 T1 이 또 터지고 같은 버퍼를 또 전사한다. 또 비고, 또 T1 을 건다.

텍스트 경로에서는 조용한 빈 반복이라 눈에 안 띄었다. **오디오가 붙으니 3초마다
Azure 호출 한 번**이 되었고 429 폭주로 드러났다.

    13:35:36  빈 전사 → 턴 미소모, T1 재무장
    13:35:39  빈 전사 → 턴 미소모, T1 재무장     ← 같은 오디오
    13:35:41  빈 전사 → 턴 미소모, T1 재무장     ← 또 같은 오디오

`_after_empty()` 가 둘로 나눈다.

| | |
|---|---|
| 버퍼가 비었다 | 말씀이 없었던 것이다. 다시 시도할 대상이 없으니 T1 을 걸지 않는다 |
| 버퍼에 뭔가 있다 | 전사가 실패한 것일 수 있다. **두 번까지** 다시 해 본다 |

어느 쪽이든 **버퍼는 비우지 않는다.** 전사 실패라면 그 안에 어르신의 말씀이 들어
있다. 다음 발화가 뒤에 붙어 함께 전사되면서 한 번 더 기회를 얻는다.

시험이 이걸 못 잡은 이유는 단순하다 — **어떤 시험도 T1 을 두 주기 이상 기다리지
않았다.** `tests/test_flow.py` [10] 이 `t1_seconds` 를 줄여 여러 주기를 돌린다.

### 전사 실패는 회차를 끝내지 않는다

`store.py` 의 쓰기, `question.py` 의 생성과 같은 규칙이다. 실패하면 빈 문자열을
돌려주고 controller 는 그걸 빈 발화로 본다 (FR-AD-312). 어르신에게는 다시 여쭙는
것으로 보이고, 회차는 산다.

`AZURE_STT_TIMEOUT` 을 예산(T2 3초)보다 긴 6초로 둔 것도 같은 이유다. 실측 p90 이
1초 언저리라 6초는 「느린 것」이 아니라 「무언가 잘못된 것」을 가르는 선이다.
**전사가 실패하면 어르신이 방금 하신 말씀이 사라진다.** 다음 질문이 몇 초 늦는 것과
비교할 일이 아니라, 늦더라도 받아 오는 쪽을 골랐다.

### 오디오는 어떻게 올라오나

    POST /api/sessions/{id}/speech/audio    본문이 오디오 바이트 그대로

JSON 으로 감싸 base64 로 넣지 않는다 — 3분의 4로 부풀고 폰에서 인코딩 비용도 든다.
mime 은 Content-Type 으로 받는다. 브라우저는 `audio/pcm;rate=16000` 으로 보낸다.

### 왜 webm 이 아니라 머리 없는 PCM 인가

MediaRecorder 가 주는 webm/mp4 는 한 녹음이 통째로 하나의 파일이다. 그런데 우리는
소리가 있는 구간만 올린다. 잘라낸 webm 조각을 이어 붙이면 헤더가 둘, 셋이 되어
어떤 디코더도 **첫 조각까지만** 읽는다. 어르신의 뒷말이 통째로 사라지는 셈이다.

머리 없는 PCM 은 이어 붙이는 것이 곧 이어 붙이는 것이다. 무음을 들어낸 자리는 그냥
없던 시간이 되고, 발화가 확정될 때 WAV 머리 하나만 씌우면 온전한 파일이 된다
(`app/session/audio.py`). `tools/replay.py` 가 녹음 파일에 하던 일과 정확히 같아서
그때 잰 숫자가 그대로 옮겨 온다.

값은 16kHz 모노 16비트, 초당 32KB다. 10초 발화가 320KB — 압축하지 않는 대신
인코딩이 없다. 타이머가 밀리초를 다투는 경로에서 이 편이 낫다.

머리의 길이 칸이 틀리면 Azure 는 오류가 아니라 **빈 전사**를 돌려주고, 화면에는
「말씀이 없었다」로 보인다. 조용히 틀리는 자리라 시험을 두었다 (`test_pcm_wrap`).

청크마다 전사하지 않는다. 회차당 수십 번이 되고, 무엇보다 말이 잘린 조각을 전사하면
정확도가 떨어진다. 발화가 확정되는 순간 모아서 한 번에 보낸다.

**소리가 있는 청크만 올리는 것은 프론트의 몫이다.** 무음까지 올라오면 T1 이 영원히
리셋되어 발화가 확정되지 않는다. 서버는 「아무것도 안 왔다」를 무음으로 읽는다 —
T1 이 이미 그 정의다. 판정을 두 군데 두면 어긋날 때 원인을 찾을 수 없다.

### 실제 목소리로 PCM 경로를 돌렸다

`python tools/replay.py --no-realtime` — 기본이 브라우저와 같은 머리 없는 PCM 이다
(`--wav` 로 통과 경로도 확인할 수 있다).

    [턴 1] turn1-130705.wav  소리 7청크(7.0초) · 무음 4청크 버림
      말씀이 끝나고 6.0초 뒤 SPEAKING
      전사  큰형이 부산에서 올라와서 영등포역까지 마중을 나왔어. …

    턴1  전사 366 · 저장 14 · 질문 922 · 전달 1707   합계 3009ms
    타이머 격발 오차 최대 16ms · 평균 8ms

6.0초는 T1 3 + T2 3 그대로다. 전사(366ms)와 질문(922ms)이 침묵 안에 완전히 숨었다.

### 제미나이가 직접 들으면 어떤가 — 재봤고, 안 바꿨다

「전사를 거치지 말고 Gemini 가 오디오를 바로 듣게 하자」는 자연스러운 제안이다.
왕복이 하나 줄고, 무엇보다 **Azure 는 글자만 넘긴다** — 머뭇거림, 떨리는 목소리,
말끝을 흐리는 것은 글이 되는 순간 사라진다. 어르신 이야기를 듣는 일에서 그게 정말
버려도 되는 것인지는 재봐야 안다. `tools/bench_audio.py` 로 셋을 같은 녹음으로 쟀다.

| | 길 | 중앙 | p90 | 전사 |
|---|---|---|---|---|
| A | 오디오 → Azure → Gemini (지금) | **1328ms** | **1518ms** | 정확 |
| B | 오디오 → Gemini 한 번에 (전사+질문) | 1587ms | 1765ms | Azure 와 10~17% 다름 |
| C | 오디오 + Azure 전사 → Gemini | 1969ms | 2222ms | 정확 (Azure) |

셋 다 예산(T2 3000ms) 안에는 든다. 그런데 **B 는 느리면서 틀렸다.**

    Azure   큰형이 부산에서 올라와서 영등포역까지 마중을 나왔어. 그때 우리는 봉천동에 살았지?
    Gemini  그냥에 부산에서 올라와서 영등포 여 까지 마중을 나왔어. 그때 우리는 풍촌동에 살았지.

「큰형이」를 **매번** 「그냥이」로 들었다. flash-lite 도, flash 도 그랬다. 사람 이름과
땅 이름이 무너지는데, 그건 회고록에서 가장 틀리면 안 되는 자리다. 게다가 잘못 들은
위에 질문을 짓는다 — 「풍촌동 그 집에서 가장 기억에 남는 소리는?」. 있지도 않은
동네를 어르신께 되묻는 것이다. flash 에서는 큰형이 마중 나온 이야기에 대고
「순애님을 다시 만났을 때」라고 물었다. **틀린 전사는 틀린 질문이 된다.**

호출 하나를 줄이는 이득도 없었다. 오디오를 프롬프트에 올리는 값이 Azure 를 따로
부르는 값보다 크다.

C 는 B 의 매력만 가져오는 길이다 — 글자는 Azure 가 정확히 넘기고 목소리는 그대로
간다. 다만 **이 녹음에서는 질문이 나아지지 않았다.** A 와 거의 같은 것을 묻고
p90 은 700ms 더 쓴다.

정직하게 적어 둘 한계 하나. 시험한 것은 **또렷하게 읽은 한 문장을 세 번 녹음한
것**이라, 애초에 읽어낼 머뭇거림도 떨림도 없었다. 감정이 실린 실제 대화에서는
C 가 달라질 수 있다. 그때 다시 재면 된다 — 도구는 남겨 두었다.

    python tools/bench_audio.py --rounds 3
    python tools/bench_audio.py --model gemini-3.5-flash

측정하다 한 번 속을 뻔했다. 처음에는 호출마다 `genai.Client()` 를 새로 만들어
A 의 p90 이 3002ms 로 나왔다 — 예산 초과로 읽고 B 로 갈아탈 뻔했다. 앱은
클라이언트를 재사용한다. **재는 쪽이 앱과 다르게 굴면 숫자가 아니라 거짓말이다.**

### 429 를 실제로 만났다

연속 호출 10회에서 걸렸고, 2초 간격을 줘도 20회 중 2번 재시도했다. `stt.py` 는
`Retry-After` 를 보고 **한 번만** 다시 시도한다 — 재시도는 예산을 먹는다.

우리 사용 패턴(회차당 3회, 수십 초 간격)이면 여유롭다. 다만 **어르신 여러 분이
동시에 쓰면 달라진다.** 실사용 전에 요금제 티어를 확인해야 한다.

## 낭독 (Azure Neural TTS)

전사와 같은 키·같은 지역을 쓴다. 호스트만 다르다.

| | 호스트 |
|---|---|
| 전사 | `{region}.api.cognitive.microsoft.com` |
| 낭독 | `{region}.tts.speech.microsoft.com` |

### 합성도 침묵 안에 숨는다 — 순서가 전부다

이 프로젝트의 핵심 설계가 여기서 한 번 더 쓰인다.

    T1 만료 ──▶ T2 카운트다운 ────────────────────────┐
            └▶ 전사 → 질문 생성 → 낭독 합성 (비동기) ┘
                                                    셋 다 끝나야 다음 질문이 나간다

질문은 실측 1.0초쯤에 준비되고 T2 최솟값은 3.0초다. 남는 2초가 합성 예산이다.
실측 합성은 **중앙 272ms · p90 437ms** — 넉넉히 든다.

    턴1  전사 0 · 저장 4 · 질문 955 · 낭독 211 · 전달 2056   합계 3015ms

`낭독(211) < 전달(2056)` 이면 소리도 침묵 안에서 다 만들어진 것이다. **이 칸이
전달보다 커지는 순간부터 어르신이 기다리게 된다.** 그래서 따로 잰다.

질문이 준비된 **뒤에** 합성을 시작하면 그 시간이 그대로 기다림이 된다.
`controller._make_question` 은 `QUESTION_READY` 를 올리기 **전에** 합성을 건다.
`tests/test_flow.py` 의 [12] 가 이 순서를 지킨다 — 조용히 어긋나도 숫자로만
드러나는 자리라서 시험이 필요했다.

### 목소리 값

| | 값 | 왜 |
|---|---|---|
| voice | `ko-KR-SunHiNeural` | 또렷하고 높낮이가 과하지 않다 |
| rate | `-8%` | 어르신 대상이다. 기본 속도는 빠르다 |
| format | 24kHz 48kbps mp3 | 폰에서 받는 시간이 짧다. 말소리에 이 이상은 안 들린다 |

`AZURE_TTS_VOICE` · `AZURE_TTS_RATE` 로 바꾼다. **실제로 들려 드리고 고를 값이지
여기서 정할 일이 아니다.**

### 소리가 없는 것은 실패가 아니다

    GET /api/sessions/{id}/question/audio
      200  audio/mpeg
      204  소리 없음 — 404 도 500 도 아니다

「질문은 있는데 소리는 없다」는 정상 상태다. 화면은 글자를 띄운 채 「낭독 끝」
버튼으로 넘어간다. 오류로 만들면 화면이 그걸 실패로 그려서, **소리가 안 나는
것과 회차가 끊긴 것을 어르신이 구분할 수 없게 된다.**

전사와 정반대의 실패 정책인 것도 같은 이유다. 전사가 실패하면 어르신의 말씀이
사라지니 예산(6초)을 넘겨서라도 받아 왔지만, 낭독이 실패해도 글자는 그대로
남는다. 그래서 낭독 타임아웃은 **1.6초**로 짧다 — 늦게 나오는 목소리보다 제때
나오는 글자가 낫다.

### tts-done 은 화면이 올린다

낭독이 끝나는 시각을 서버는 알 수 없다. 끝까지 튼 쪽이 화면이라, 거기서 올려야
T1 이 정확한 순간부터 돈다. 몇백 밀리초 어긋나면 「무음 3초」가 무음 2.6초가 된다.

**iOS 사파리는 사용자 동작 없이 소리를 내주지 않는다.** 회차를 여는 탭에서 무음
wav 를 아주 잠깐 틀어 잠금을 푼다(`src/speaker.ts`). 요소를 매번 새로 만들면
잠금이 풀리지 않아서 <audio> 하나를 끝까지 돌려쓴다.

낭독 중에는 마이크 판정을 끈다(`recorder.setActive(false)`). 안 끄면 스피커에서
나온 질문이 마이크로 되돌아와 판정이 열린 채로 남고, **수음이 열리는 순간 그
꼬리가 어르신의 첫마디인 양 올라간다.**

## 저장 (PostgreSQL)

`store.py` 가 `migrations/` 가 정의한 표에 내린다. 컨트롤러가 부르는 지점은 넷이다.

스키마를 바꿀 때는 **`migrations/` 에 새 번호를 더한다.** 이미 적용된 파일은
고치지 않는다 — `migrate.py` 가 체크섬을 들고 있어서, 고치면 다음 기동이 조용히
지나가는 대신 소리를 내며 멈춘다. DB 에 붙었는데 스키마를 못 올리면 **서버가 뜨지
않는다**: 이 파일의 쓰기 함수들이 실패를 삼키므로, 스키마가 틀린 채로 뜨면 모든
INSERT 가 조용히 실패하고 어르신은 한 시간을 말씀하시고 아무것도 남지 않는다.

| 시점 | 하는 일 |
|---|---|
| `start()` | `session` INSERT + 0번 조각(씨앗) |
| `_confirm()` | **확정 즉시** `turn` INSERT. 지연 숫자를 기다리지 않는다 |
| `_maybe_advance()` | `turn.latency` UPDATE (`decision` 은 건드리지 않는다) |
| 종료 3경로 | `session.closed_reason` = `finish` / `abort` / `max_turn` |

스키마는 기동 시 `open_pool()` 이 적용한다. 전부 `CREATE TABLE IF NOT EXISTS` 라
몇 번을 걸어도 같고, 마이그레이션 도구를 쓰지 않기로 한 이상 이게 가장 싸다.

### DB 가 없어도, 끊겨도 회차는 돈다

이 파일의 유일한 규칙이다. 어르신이 말씀하시는 도중에 Postgres 가 한 번 비틀거렸다고
인터뷰가 끊기면 안 된다. 그래서 **모든 함수가 실패를 삼키고 로그만 남긴다.**

    11:25:42 store  DB 없이 간다 (...) — 세션이 메모리에만 남는다

조각은 이미 컨트롤러의 메모리에 있고 화면은 그걸로 계속 돈다. 잃는 것은 그 턴의
기록뿐이고, 그건 회차가 끊기는 것보다 싸다. 다만 조용히 넘어가지는 않는다 —
ERROR 로 남겨 나중에 셀 수 있게 한다.

기동도 마찬가지다. DB 에 못 붙어도 서버는 뜬다. 안 그러면 프론트 작업이 Postgres
셋업을 기다리게 된다.

### 읽기는 실패를 삼키지 않는다 — 쓰기와 정반대다

같은 파일 안에서 규칙이 뒤집히는 자리라 적어 둔다.

| | 실패하면 | 왜 |
|---|---|---|
| 쓰기 | 삼키고 로그만 | 인터뷰가 끊기면 안 된다. 잃는 건 그 턴 하나 |
| **읽기** | **StoreUnavailable 로 올린다** | 빈 목록을 주면 「기록이 없습니다」가 뜬다 |

두 번째가 중요하다. 못 읽은 것을 없다고 말하면 **어르신에게는 조각이 사라졌다는
말**이 된다. 조각은 DB 에 그대로 있는데 화면만 그렇게 말하는 것이다.

있는 것과 못 읽은 것은 다른 사건이고, 화면도 다르게 말해야 한다.

    503   지금은 기록을 불러올 수 없습니다. 조각은 그대로 있습니다.
    200 + 빈 목록   아직 저장된 회차가 없습니다.

`main.py` 의 `_read()` 가 그 경계다. `App.tsx` 의 `loadSaved()` 도 503 만 따로 잡는다.

### 읽는 경로 둘

| | 보는 자료 | 재시작 뒤 |
|---|---|---|
| `GET /api/sessions/{id}` | 메모리의 SessionController | **사라진다** (404) |
| `GET /api/sessions/{id}/record` | DB | 남는다 |
| `GET /api/sessions?limit=` | DB. 최근 순 목록 | 남는다 |

**일부러 합치지 않았다.** 재시작 뒤에 조각을 *보는* 것과 회차를 *이어서 하는* 것은
전혀 다른 일이다. 이어 하려면 상태 머신과 타이머까지 되살려야 하는데, 서버가 내려간
동안 어르신 쪽 화면도 이미 멈춰 있었다. 그 상태로 T1 을 다시 거는 건 위험하다.
지금은 보는 것까지만 한다.

`record` 는 **소유자를 확인한다.** 남의 것이면 403 이 아니라 404 다 — 403 은
「있긴 있다」를 알려주는 셈이라 id 를 넣어 보며 존재를 확인할 수 있다. 다만 지금은
`X-User-Id` 를 그대로 믿으므로 헤더를 바꾸면 통과한다. 로그인이 붙을 때 이 줄이
그대로 실효를 가진다.

조각은 `created_at` 이 아니라 **`idx` 순으로 준다** (FR-AD-401). 0번(씨앗)과 1번이
같은 초에 들어가면 시각 정렬은 순서가 뒤집힌다.

### asyncpg 가 까다로운 두 곳

`store._sid()` 가 있는 이유다. 컨트롤러는 `session_id` 를 `str` 로 들고 다니지만
(HTTP·JSON 에 그대로 나가야 한다) **asyncpg 는 UUID 컬럼에 `str` 을 받지 않는다.**
`t2_seconds` 도 `NUMERIC` 이라 `float` 이 아니라 `Decimal` 이어야 한다.

## 배포할 때

절차는 **`docs/배포.md`** 에 있다 — 도메인부터 Cloudflare Tunnel, 재부팅 생존,
확인 목록까지. 여기서는 코드가 무엇을 스스로 하는지만 적는다.

**`.env` 에 `PUBLIC_ORIGIN` 을 적는 것이 스위치다.** 주소를 담는 칸이 아니다.
이 값이 있으면 서버가 개발용 편의를 스스로 닫는다 — 끄는 것을 잊게 두지 않으려고
따로 스위치를 만들지 않았다.

| | 개발 (`PUBLIC_ORIGIN` 없음) | 배포 (있음) |
|---|---|---|
| CORS 허용 | `localhost:5173` 포함 | **뺀다.** 화면을 이 서버가 내므로 같은 출처다 |
| `/docs` · `/openapi.json` | 열림 | **닫힘** (`DOCS=1` 로 되살린다) |
| 신원 쿠키 `Secure` | https 일 때만 | **항상** |
| `TRUST_PROXY` | `off` | `cf` — 터널 뒤에서 방문자 주소를 세려면 필요하다 |

`/docs` 를 닫는 이유가 하나 더 있다. FastAPI 는 라우트의 docstring 을 **그대로
`/docs` 에 노출한다.** `main.py` 의 주석에는 개발 중에 알아야 할 것들이 적혀
있는데, 그중 일부는 공개 문서에 뜨면 곤란하다.

    GET /api/sessions/{id}   "소유자 검사가 없다. session_id 만 알면 남의 조각이 보인다"
    POST .../abort           "「정의되지 않은 전이는 409」 원칙의 유일한 예외다"

**둘 다 사실이고 적어 두는 게 맞다** — 개발 중에 `/docs` 를 눌러 보는 사람이 바로
알아야 하는 내용이다. 배포에서 자동으로 닫히니 주석을 내릴 필요는 없다. 소유자
검사는 ⑤ 로그인이 붙을 때 실제로 막히고, 그때 저 줄이 지워진다. **이 항목이 남아
있다는 건 아직 안 막혔다는 표시다.**

기동 로그 첫 줄이 그날의 자세를 말한다.

```
api  자세 — 공개주소=https://… · CORS허용=(없음·동일출처) · docs=닫힘 · 프록시=cf · 워커=1
```

워커가 둘 이상이면 여기에 빨간 줄이 선다. 회차 레지스트리가 프로세스 메모리라
**워커는 반드시 하나여야 한다** — `run.ps1` 이 그렇게 띄운다.

`.env`와 `web/`은 `.gitignore`에 있으니 저장소에 올라가지 않는다. 터널 URL이 코드에 박힌 곳도 없다 — 전부 환경변수를 지난다.

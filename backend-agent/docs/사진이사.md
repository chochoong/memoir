# 사진 이사 — pg → Blob

**아직 코드가 없다.** 이 문서는 절차를 먼저 정해 두는 것이다. 이사는 사진이
많아진 뒤에, 즉 「지금 당장 해야 하는 상황」에서 하게 된다. 그때 순서를
즉흥으로 정하면 반드시 한 단계를 빠뜨린다.

## 옮기는 것은 (키, 바이트) 쌍 하나뿐이다

001 의 `photo` 테이블은 처음부터 `storage_key` 를 들고 있었다. 그 한 열 덕분에
**DB 는 바이트가 어디 있는지 모른다** — 키만 안다.

```
photo 행                                   저장소
  photo_id   3f2a…                          photos/2026/09/3f2a…/view.jpg → bytes
  storage_key photos/2026/09/3f2a…/view.jpg
  bytes      7439                     ↑ 이 키는 저장소가 바뀌어도 그대로다
  sha256     …
```

그래서 이사에 **스키마 마이그레이션이 없다.** `photo` 도 `photo_blob` 도
건드리지 않는다. 옮기는 일은 「모든 키의 바이트를 새 저장소에 복사하고,
`PHOTO_STORE` 를 바꾸고, 재시작한다」로 끝난다 — 아래 한 가지만 빼면.

## 왜 「복사하고 환경변수 바꾸기」로 안 끝나는가

`photostore.current()` 는 저장소를 **하나만** 돌려준다. 그래서 전환하는 순간
옛 저장소는 없는 것이 된다.

```
복사 시작 ─────────── 복사 끝 ─── 전환
     │                              │
     └─ 이 사이에 올라온 사진은 옛 저장소에만 있다 → 전환 뒤 안 보인다
```

서비스를 멈추고 복사하면 이 구간이 없어지지만, 그러려면 어르신이 이야기하시는
중간에 화면이 멈춘다. 그래서 **읽기 폴백 기간**을 둔다.

```
MirrorStore(primary=blob, fallback=pg)

  put     primary 에만        ← 새 사진은 처음부터 새 곳에
  get     primary → 없으면 fallback
  delete  **둘 다**           ← 한쪽만 지우면 지운 얼굴이 남는다
  exists  둘 중 하나라도
```

`delete` 가 둘 다인 것이 이 표에서 제일 중요하다. 사진은 얼굴이고, 지워 달라는
요청은 한 번만 온다.

## 순서

각 단계가 **서버 재시작**을 동반한다 (`current()` 가 저장소를 한 번 만들어
재사용한다). 재시작은 진행 중인 회차를 끊으므로 어르신이 안 쓰실 시간에 한다.

### 0단계 — 옮기기 전에 셈이 맞는지 본다

이사는 어긋난 것을 옮기면 어긋난 채로 두 배가 된다. 먼저 세 수를 맞춘다.

```sql
-- ① DB 가 아는 사진
SELECT count(*), sum(bytes) FROM photo;

-- ② 저장소가 가진 바이트
SELECT count(*), sum(octet_length(bytes)) FROM photo_blob;

-- ③ 짝이 안 맞는 것
SELECT storage_key FROM photo      WHERE storage_key NOT IN (SELECT storage_key FROM photo_blob);
SELECT storage_key FROM photo_blob WHERE storage_key NOT IN (SELECT storage_key FROM photo);
```

| 어긋남 | 뜻 | 할 일 |
|---|---|---|
`photo` 에만 있다 | **바이트가 없는 행이다.** 사고다 | 옮기기 전에 원인부터. 그 행은 영영 500 을 낸다 |
`photo_blob` 에만 있다 | 고아 바이트. 보상 삭제가 실패한 잔해다 | **옮기지 않는다.** 여기서 지운다 |

### 1단계 — Azure 쪽 준비

컨테이너는 **private** 이다. 익명 읽기를 켜지 않는다. 우리는 SAS 서명 URL 도
쓰지 않는다 — `PhotoStore` 에 `url()` 이 없는 것이 그 결정이고, 사진은 언제나
`GET /api/photos/{id}` 로만 나간다.

연결 문자열은 `.env` 에 넣는다. `.env` 는 `.gitignore` 에 있다.

```ini
PHOTO_STORE=pg
AZURE_BLOB_CONNECTION=…
AZURE_BLOB_CONTAINER=memoir-photos
```

### 2단계 — 이중 읽기를 켠다 (아직 복사 전)

```ini
PHOTO_STORE=mirror
PHOTO_STORE_PRIMARY=blob
PHOTO_STORE_FALLBACK=pg
```

재시작. 이 순간부터 **새 사진은 Blob 에만** 들어가고, 옛 사진은 폴백으로 읽힌다.
화면에서는 아무것도 달라지지 않는다.

### 3단계 — 복사

```powershell
python -m tools.photo_move --from pg --to blob --dry-run
python -m tools.photo_move --from pg --to blob
```

`photo.storage_key` 를 훑어 없는 것만 복사한다. 중간에 끊겨도 다시 돌리면 이어
간다(이미 있는 키는 건너뛴다).

### 4단계 — 대조

복사한 개수만 세면 안 된다. **바이트가 같은지**를 본다.

```
키 개수        photo 행 수와 같은가
바이트 합      SUM(photo.bytes) 와 같은가
표본 sha256    무작위 20장을 Blob 에서 내려받아 photo.sha256 과 맞는가
```

sha256 은 **원본**의 해시이고 저장된 것은 화면용 변형이라 직접 비교되지 않는다.
비교 대상은 `photo.bytes`(저장된 바이트 수)와 내려받은 길이다. 표본은 그 길이가
맞는지를 본다.

### 5단계 — 폴백이 0이 될 때까지 둔다

`MirrorStore` 는 폴백으로 읽은 횟수를 로그에 남긴다.

```
photo  이사 — 폴백 읽기 0회 / 최근 24시간   ← 이 줄이 나오면 옮길 것이 남지 않았다
```

**이 수가 0이 되는 것이 전환의 근거다.** 날짜로 정하면 늦거나 이르다.

### 6단계 — 전환

```ini
PHOTO_STORE=blob
```

재시작. 옛 바이트(`photo_blob` 표)는 **바로 지우지 않는다.** 며칠 둔다.

```sql
-- 충분히 지난 뒤에
TRUNCATE photo_blob;
```

## 되돌리기

**`PHOTO_STORE=pg` 로 되돌리면 안 된다.** 2단계 이후에 올라온 사진은 Blob 에만
있어서, pg 로 되돌리면 그것들이 전부 안 보인다. 되돌릴 때도 mirror 로 간다 —
방향만 뒤집는다.

```ini
PHOTO_STORE=mirror
PHOTO_STORE_PRIMARY=pg
PHOTO_STORE_FALLBACK=blob
```

`photo_blob` 을 TRUNCATE 한 뒤에는 되돌릴 길이 없다. 그것이 6단계에서 며칠
기다리는 이유다.

## 이 문서가 요구하는 코드 (아직 없다)

| | |
|---|---|
`BlobStore` | `azure-storage-blob` 로 put·get·delete·exists 넷. `PhotoStore` 규약 그대로 |
`MirrorStore` | 위 표의 네 줄. 폴백 읽기 횟수를 센다 |
`_BACKENDS` 에 등록 | `make()` 가 모르는 값에 **멈추므로** blob·mirror 를 정식으로 넣어야 한다 |
`tools/photo_move.py` | `--from`·`--to`·`--dry-run`. 이미 있는 키는 건너뛴다 |

## 서두를 이유가 없다는 것도 적어 둔다

화면용 변형은 1024×768 에 **7KB 남짓**이다(2400×1800 67KB 원본의 실측값).
사진 1000장이 7MB 다. Postgres 가 이 크기에 힘들어하는 일은 없다.

옮길 이유는 용량이 아니라 **분리**다 — DB 백업에서 바이트를 빼고, 정적 서빙을
CDN 에 맡기고, DB 를 작게 유지하는 것. 그 필요가 실제로 생겼을 때 이 문서를
편다. 쓰지 않을 코드를 미리 쓰면 쓸 때쯤 낡아 있다.

# 백엔드 인수인계 — 충님께

2026-11-11 기준 `develop`(7400e51)의 코드를 읽고 적었다. 코드는 고치지 않았다. 아래에서 "결정"이라고 적은 것은 백엔드 담당자가 정할 일이며, 이 자료가 대신 정하지 않는다. 상대 경로는 `backend-agent/첨부프롬프트_md/문체/` 기준이다.

## 1. 지금 서비스에서 문체가 지나가는 길

| 자리 | 지금 | 문체 3종과의 관계 |
|---|---|---|
| `backend-agent/app/session/style.py` | `style` 값의 목록. `DEFAULT = "spoken"` · `SUPPORTED = ("spoken",)`. 머리말에 `novel`(소설체) · `cyworld`(싸이월드체)가 예약돼 있다. 모르는 값은 400 `unsupported_style`. **엽서와 자서전이 같이 쓴다** | 새 문체의 값은 여기에 들어가야 한다. `novel` 은 예약된 이름과 같다. `essay` · `literary` 는 새 값이다 → `remaining_decisions.md` 결정 1 |
| `backend-agent/app/main.py` `POST /api/memoirs/preview` · `POST /api/memoirs` | 요청 본문의 `style` 을 `styles.pick()` 으로 거른다. 없으면 구어체 | 화면이 보낸 문체가 여기로 들어온다 |
| `backend-agent/app/session/memoir.py` `generate(recs, ids, user_id, style, …)` | `style` 을 받아 응답에 그대로 싣는다. **모델에는 보내지 않는다** | 문체에 따라 집필을 가르는 자리는 아직 없다. 여기가 분기점 후보다 |
| `backend-agent/app/session/memoir.py` `_draft_pipeline` → `memoir_pipeline.run(…)` | `MEMOIR_ENGINE=pipeline` 일 때 다섯 단계(분석 · 목차 · 장 집필 · 편집 · 검증). 늘 v7 지시문 | 세 문체는 이 다섯 단계의 '장 집필'과 계약이 다르다(§3 · §4) |
| `backend-agent/app/session/memoir_pipeline.py` `prompt(stage)` | 공통 지침을 앞에 붙이고, 코드 울타리 줄을 지운다 | **문체 프롬프트를 이 함수로 읽으면 안 된다**(§2) |
| `backend-agent/app/session/memoir.py` `pipeline_result` | 응답 `{status, style, title, chapters[{no, title, paragraphs[{sentences[{text, turns}]}]}], body, sources, verification, run}` | 문장과 턴 단위다. 세 문체의 출력은 문단 단위다(§5) |
| `backend-agent/app/session/memoir_jobs.py` · `GET /api/memoirs/{job_id}` | 긴 생성을 일감으로 돌리고 진행을 알린다 | 문체 3종은 한 장에 1~6분이 걸렸다 — 일감 경로가 맞다(§7) |

**지금은 어떤 운영 코드도 문체 프롬프트를 읽지 않는다.** 이 자료를 올려도 서비스 동작은 바뀌지 않는다.

## 2. 프롬프트 로딩 — 파일 그대로

세 프롬프트는 **파일의 바이트를 UTF-8로 읽은 문자열 그대로** 쓴다. 검증한 호출이 그랬다.

- 앞뒤에 다른 지침을 붙이지 않는다. 기존 `prompt()` 는 공통 지침을 앞에 붙인다 — 문체 프롬프트에 쓰면 실험과 다른 입력이 된다.
- 코드 울타리(```` ``` ````) 줄을 지우지 않는다. 수필체 · 문학체 프롬프트의 출력 형식 예시가 울타리 안에 있다. 기존 로더는 그 줄을 지운다.
- 끝의 줄바꿈 · 빈 줄을 다듬지 않는다(`strip()` 금지). 호출 기록의 프롬프트 해시가 파일 해시와 같아야 한다.
- **줄바꿈은 LF 다.** Windows 에서 텍스트 모드로 읽으면 내용은 같지만, Git 이 파일을 CRLF 로 풀어 놓으면 해시가 달라진다. 문체 폴더의 `.gitattributes` 가 변환을 끈다 — 지우지 않는다. 읽을 때는 바이트로 읽어 UTF-8로 푸는 것이 안전하다.
- 소설체는 `{{SOURCE_TEXT}}` 한 군데만 바꾼다. 다른 `{{…}}` 는 없다. 수필체 · 문학체에는 자리표시가 없다.
- 파일 이름은 실험에서 쓰던 그대로 두었다. 정식 명칭은 `style_manifest.json` 의 매핑으로 관리한다.
- 실행 기록에 **프롬프트 해시**를 남기면 "어느 프롬프트로 쓴 글인가"를 나중에 대조할 수 있다(`backend-agent/tests/test_style_handoff.py` 가 같은 값을 본다).

메시지 구성(검증된 호출):

| 문체 | 시스템 | 사용자 | 출력 형식 강제 |
|---|---|---|---|
| 수필체 | 프롬프트 파일 | 장 자료 묶음 | JSON 스키마(구조화 출력) |
| 문학체 | 프롬프트 파일 | 장 자료 묶음 | JSON 스키마(구조화 출력) |
| 소설체 | **없음** | 원문을 끼운 프롬프트 전체 | 없음 |

## 3. 필수 분석 자산 — 수필체 · 문학체

두 문체는 프롬프트만으로 돌지 않는다. **장 자료 묶음**을 만들 분석 결과가 있어야 하고, 서비스의 지금 분석(v7)에는 그 필드의 절반이 없다.

| 묶음에 필요한 것 | 지금 서비스의 분석(v7)에 있는가 |
|---|---|
| 사실 `id` · `text` · `source` · `certainty` | **있다** — 같은 값 체계. id 모양만 다르다(서비스 `f<숫자>` · 실험 `f<이야기>-<번호>`) |
| 사실이 나온 이야기(턴) | 있다 — `facts[].turns` |
| 이야기별 반드시 남길 세부(`must_keep`) | **없다** |
| 이야기별 감정 기록(`emotion_notes`) · 지금의 회고(`reflections_now`) | **없다** |
| 이야기별 인물 · 때 · 곳 · 들은 이야기 · 직접 인용 | 일부만 |
| 장별 주의(`fiction_notes`) · 다른 장과의 겹침(`avoid_overlap`) | **없다** |
| 장별 집필 방향(`center_scene` · `emotion` · `direction`) — 수필체만 | **없다** |
| 장에 든 이야기 | 있다 — 목차 |

### A. 저장소에 함께 있어야 재현되는 자산

| 자산 | 이번 전달 | 비고 |
|---|---|---|
| 분석 출력 스키마 | **넣었다** — `schemas/analysis_output.schema.json` | 실험 실행기의 스키마 그대로 |
| 장 자료 묶음 조립 규칙 | **넣었다** — `reference/bundle_reference.py` | 실제로 보낸 입력 8건과 글자까지 같다. 운영 코드가 아니라 규격을 대신하는 참조 구현이다 |
| 가상 입력 예시 | **넣었다** — `examples/analysis.sample.json` · `stories.sample.json` · 묶음 2개 | 실제 인터뷰가 아니다 |
| **분석 지시문** | **넣었다(안전 사본)** — `analysis/0_원문분석_목차통합_안전사본.md` | 위 스키마의 출력을 만드는 지시문. 실험에 쓴 원본의 예시 한 곳에 실제 인터뷰의 인물 이름이 있어, 그 이름만 가상 식별자(`가상인물_A`)로 바꾼 사본이다. 원본은 올리지 않는다 → `analysis_prompt_safety.md` |
| 제목 후보 평가 · 선정 지시문과 로직 | 넣지 않았다 | 수필체의 확정 제목을 만드는 단계. 문체 프롬프트의 범위를 넘고 실험 실행기와 한 덩어리다 |

### 분석 지시문을 쓰는 법(실험에서 한 그대로)

| | 값 |
|---|---|
| 시스템 | `analysis/0_원문분석_목차통합_안전사본.md` 를 파일 그대로(§2의 로딩 규칙과 같다 — 공통 지침을 붙이지 않고, 다듬지 않는다) |
| 사용자 | 이야기마다 `## 이야기 N` 한 줄 · 빈 줄 · 원문 전문. 이야기 사이는 빈 줄 하나. 끝에 맺는 문장 하나 |
| 맺는 문장(실험의 두 가지) | 여러 장: "위 이야기 10개를 지시대로 분석하고 2~3개 장으로 설계해 JSON 하나만 출력하세요." / 한 장: "위 이야기 3개를 지시대로 분석하고, 이번에는 **장 하나(c1)** 로 설계해 JSON 하나만 출력하세요. 세 이야기 모두 그 한 장에 들어갑니다(장 수 1)." |
| 출력 | `schemas/analysis_output.schema.json` 을 구조화 출력으로 강제한다. 잘린 응답은 쓰지 않는다 |
| 모델 · 설정(실험) | `claude-fable-5-1` · effort high · 스트리밍 · 재시도 0 · 출력 상한 32,000 |

- 이 지시문은 한 호출로 **이야기별 분석(1부)과 장 설계(2부)**를 함께 낸다. 장 제목은 정하지 않고 후보 6개(`title_basis.candidates`)만 낸다 — 확정 제목은 다른 단계에서 온다(§6).
- **서비스의 지금 분석과는 다른 지시문 · 다른 스키마다.** 서비스는 `backend-agent/첨부프롬프트_md/파이프라인/1_분석_v7.md` 를 공통 지침과 함께 읽고, 지킬 세부 · 감정 기록 · 장별 설계를 내지 않는다. 안전 사본은 서비스 로더가 읽는 폴더(`파이프라인/` · `파이프라인_통합/`)가 아니라 문체 폴더에 두었다 — 올려도 지금 서비스의 동작이 바뀌지 않는다.
- **안전 사본은 실험에 쓴 원본에서 예시의 이름 하나만 가상 식별자로 바꾼 것**이다(`analysis_prompt_safety.md`). 규칙 · 필드 · 출력 구조는 같다. 다만 이 사본으로 모델을 불러 본 적은 없다 — 원본 때와 같은 분석이 나오는지는 실서비스 연동 후 확인한다.

### B. 백엔드가 구현해야 하는 것

1. **분석 호출** — 위 표대로 원문을 안전 사본의 지시문과 함께 보내 스키마의 JSON 을 받는다. 모델 · 상한 · 일감 경로는 정해야 한다.
2. **장 자료 묶음 조립** — 참조 구현을 서비스 코드로 옮긴다. 머리 문구를 바꾸지 않는다.
3. **확정 제목의 공급**(수필체) — 분석은 후보만 낸다. 확정 · 검증된 제목이 묶음에 들어가야 한다(§6).
4. **민감 여부 판정** — 호출하는 쪽이 정한다. 실험의 규칙(낱말 + 사람이 고른 목록)은 이 자료에 없다.
5. **문체에 따른 분기 · 모델 호출 · 상한**(§7), **응답으로의 변환**(§5), **사실 대조**(§6).
6. 일화 누락 검사 — 분석의 지킬 세부가 본문에 남았는지 보는 검사. 실험 실행기에만 있다.

`backend-agent/tools/memoir_literary.py` 는 이미 `develop` 에 있다 — 수필체 출력 스키마와 사실 대조(`check_essay`)가 들어 있고, 실험 폴더의 것과 해시가 같다.

### C. 검증되지 않은 의존성

1. **서비스의 v7 분석을 넓혀 만든 묶음**으로 문체가 유지되는가 — 돌려 본 적이 없다.
2. **분석 지시문의 판** — 수필체(결혼 주제)는 현재 판으로, 문학체 기준 원고와 수필체 3장(가장 주제)은 앞선 판으로 만든 분석을 썼다. 두 판은 이야기별 분석 절이 글자까지 같고 목차의 제목 절만 다르다. 현재 판의 분석으로 문학체를 돌린 기록은 없다.
3. **분석 모델** — Fable 5.1 로만 만들었다. 다른 모델의 분석 결과로 묶음을 만든 기록은 없다.
4. 문학체의 참고 분량과 민감 문구 — 한 조합만 검증됐다(`input_output_contract.md` §2).
5. **안전 사본으로 실제 분석을 돌린 적이 없다.** 예시의 이름 하나가 달라졌을 뿐이지만, 모델이 내는 분석이 원본 지시문 때와 같다고 말할 수 없다 — 실서비스 연동 후 원본 때의 분석 결과와 나란히 한 번은 확인해야 한다.

### 소설체

분석 결과가 필요 없다. 그 장의 원문만 있으면 된다. 대신 사실 원장을 주지 않으므로 **사실 보존은 프롬프트의 지시에만 달려 있다**(§6).

## 4. 소설체가 1판과 달라진 것

- 정식 소설체는 구운몽ST **원본이 아니라 최소 수정 v1** 이다. 원본에서 꿈 · 기시감 · 미래 예지 서술을 요구하는 구절만 뺐다 — 손댄 줄 14 · 지운 문단 2 · 111줄 중 93줄은 글자까지 같다. 대화 · 사실 보존 · 출력 절은 그대로이고, 새 금지 규칙은 넣지 않았다. 전체 대조표는 `novel_prompt_diff.md`.
- 수정본은 결혼 주제의 이야기 세 개로 **한 번** 돌려 봤다(Claude Sonnet 5.5). 꿈 · 기시감 · 예지 서술은 나오지 않았고, 따옴표 발화 33개 · 세 일화 모두 유지 · 사실 32개 중 그대로 27 · 바뀜 0 이었다(판정은 Claude Code 의 읽기다 — 사람의 블라인드 평가가 아니다).
- 메시지 구성이 확인됐다 — 사용자 메시지 하나 · 시스템 없음(원본의 팀 공유 실행 기록과 토큰 수가 일치했고, 수정본도 같은 방식으로 돌렸다).
- **다애님이 수정본의 정식 사용을 승인했다.** 매니페스트의 `approval` 은 「다애님 승인 완료 — 소설체 최소 수정 v1」이다(사용자가 전달한 승인이다 — 승인 날짜와 증빙 파일은 확인되지 않아 적지 않았다).
- 장 단위로 이어 쓰려면 템플릿의 `[앞 장에서 이어받을 내용]` 을 채워야 한다. **그렇게 돌린 기록은 없다.**

## 5. 생성 출력 — 응답 모양과의 간격

지금 응답은 **문장마다 `text` 와 `turns`(근거가 된 턴)**를 싣는다. 세 문체는 문단 문자열을 낸다.

| 응답 필드 | 수필체 · 문학체에서 만드는 법(설계안 — 구현 · 검증 안 됨) | 소설체 |
|---|---|---|
| `chapters[].title` | 목차의 확정 제목. **모델이 낸 `title` 을 쓰지 않는다** | 목차의 제목(모델은 제목을 내지 않는다) |
| `chapters[].paragraphs[].sentences[].text` | 문단을 문장으로 나눠야 한다. 문학체는 문단 안 줄바꿈과 조각 문장이 있어 **문장 분리 규칙이 표현을 건드릴 수 있다** | 줄 단위(대사) · 빈 줄 단위(장면)가 자연스러운 경계다 |
| `sentences[].turns` | `facts[].where` 가 든 문장 → 그 사실의 id → 사실의 이야기 번호. 사실이 없는 문장(은유 · 창작 · 원문의 감정)은 **빈 목록**이 된다 — 문학체 검증 원고는 189문장 가운데 사실의 자리가 27곳뿐이다 | **만들 근거가 없다**(사실 표시가 출력에 없음) |
| `body` | 지금은 문장마다 줄을 바꿔 합친다 → 문단 경계가 사라진다. **문단 사이 빈 줄 · 문단 안 줄바꿈을 지키는 방식이 필요하다** | 같다 — 본문 텍스트를 그대로 |
| `sources[]` | `turns` 와 같은 한계 | 없음 |
| `verification.state` | 사실 대조 결과(§6) | 대조 수단 없음 → `not_run` |

→ 응답 규격을 문단 단위로 넓힐지, 문체 출력을 문장 단위로 바꿔 넣을지는 결정 사항이다(`remaining_decisions.md` 결정 4). **문장 단위로 바꿔 넣을 때 문학체의 줄바꿈과 소설체의 대사 줄이 보존되는지는 반드시 실제 원고로 확인해야 한다.**

저장 · 출력:

- 원고는 **문단 배열 그대로** 저장한다(수필체 · 문학체). 소설체는 본문 텍스트 그대로.
- Markdown · PDF 로 낼 때 문단 사이 빈 줄 · 문단 안 줄바꿈을 지킨다(줄 끝 공백 둘 또는 `<br>`).
- 사실 표시 · 각색 기록 · 실행 정보(모델 · 프롬프트 해시 · 종료 사유)는 원고와 함께 둔다.
- 요청 기록에는 실제 인터뷰가 들어간다. 지금 서비스는 로그에 원문 · 본문을 남기지 않는다 — 같은 원칙을 지킨다.

## 6. 제목 · 사실 · 각색의 위험

### 제목

- **검증된 제목만 집필 입력으로 준다.** 수필체는 확정 제목이 없으면 묶음을 만들 수 없다. 문학체는 임시값 「제목 미확정」으로 돌고, 임시값을 최종 제목으로 저장하지 않는다.
- **모델이 낸 `title` 은 믿지 않는다.** 수필체 지시문은 제목을 새로 지으라고 적혀 있고, 실제로 다른 제목을 낸 모델이 있었다. 다르면 기록만 하고 목차의 제목을 쓴다.
- **오래된 목차를 그대로 넘기는 경로를 막는다.** 실험에서 제목 규칙이 생기기 전에 만든 목차를 여러 실행기가 계속 읽어, 낡은 제목이 원고에 반복해 들어간 일이 있었다. 목차(제목)에 언제 · 어느 규칙으로 정했는지를 붙여 두고 집필 전에 확인하는 것을 권한다.
- 실험의 제목 선정은 적격 제목이 없으면 **제목을 비우고 멈춘다.** 차순위를 자동으로 올리지 말고 사람에게 넘긴다.
- 소설체는 제목을 내지 않는다 — 제목은 다른 경로에서 와야 한다.

### 사실 · 각색 — 세 가지를 섞지 않는다

| 구분 | 뜻 | 수필체 | 문학체 | 소설체 |
|---|---|---|---|---|
| **실제 사실** | 원문에서 확인한 사건 · 인물 · 관계 · 행동 · 결과 | `facts[].where` 로 본문과 대조 | 같다 | **출력에 표시 없음** |
| **문학적 표현** | 사실을 바탕으로 한 비유 · 상징 · 감각 · 장면 재구성 | `fiction` 에 전부 | 은유는 싣지 않음(중심 이미지와 오해 소지만) | 기록 없음 |
| **창작된 구체적 내용** | 원문에 없는 대화 · 행동 · 독백 · 주변 상황 | `fiction` 에 전부(대사는 금지) | `fiction` 에 전부(대사는 `가상 대화`로) | 기록 없음 |

- 사실 대조는 `where` 가 본문에 **글자 그대로** 있는지 보는 방식이다. 모델이 `where` 를 "…"로 이어 적으면 실패한다(실제로 있었다 — 고쳐서 통과시키지 않았다).
- 문학체는 **사건은 그대로 두고 화자의 깨달음 · 회고를 새로 세우는 문장**이 나온다(검증 원고에서 9곳). 사실 검사로는 잡히지 않는다. 본인 확인 절차가 필요하다.
- **소설체는 사실 · 각색을 기계로 검증할 수단이 없다.** 따옴표 발화는 원문에 직접 인용이 없으면 전부 창작이고, 실존 인물의 말을 짓는다. 본문에서 실제 발언과 구분되지 않는다. 원문과 맞대는 사후 대조(사람 또는 별도 검증 호출)가 필요하다 — 이번 범위에서 만들지 않았다.
- 소설체 수정본은 꿈 · 기시감을 **금지하지 않는다**(요구하던 구절을 뺐을 뿐이다). 한 번의 실행에서는 나오지 않았으나, 다시 나오지 않는다는 보장은 아니다.
- 수필 검사기의 '같은 문장 반복' · '강조어' · '확장률' 규칙은 문학체에서 오탐이다(후렴과 긴 분량은 의도). **사실 규칙과 문체 규칙을 나눠서** 판정해야 한다. 검사기의 기준을 낮추라는 뜻이 아니다.

## 7. 모델 · 시간 · 비용 — 검증된 값

모델은 백엔드 담당자가 정한다. 아래는 **실제로 돌려 본 조합**이다. 서비스의 기본 모델(`gemini-3.5-flash-lite`)로는 세 문체 모두 **돌려 본 적이 없다.**

| 문체 | 모델 | 설정 | 한 장의 실제 값 |
|---|---|---|---|
| 수필체 | `gpt-6.1-sol` | reasoning effort medium · 출력 상한 96,000 · strict JSON 스키마 | 새 주제 1장 완성 · 사실 32/32 |
| 수필체 | `claude-sonnet-5-5` | effort high · 출력 상한 65,536 | 입력 약 12천 · 출력 22~31천 토큰 · $0.24~0.33 · 140~183초 |
| 수필체 | `claude-fable-5-1` | effort high · 출력 상한 32,000 | $1.1~1.7 · 218~329초 · **3장 중 1장이 상한에서 잘림** |
| 문학체 | `claude-sonnet-5-5` | effort high · 출력 상한 128,000 · 스트리밍 · temperature 미설정 | 입력 13,838 · 출력 47,856 토큰 · **$0.51 · 321초** — 사용자가 만족한 기준 원고 |
| 소설체(수정본) | `claude-sonnet-5-5` | effort high · 출력 상한 65,536 · 스트리밍 · 시스템 없음 | 입력 5,765 · 출력 7,891 토큰 · **$0.09 · 71초** |

- **문학체와 소설체 수정본은 Claude Sonnet 5.5에서만 검증됐다.** 다른 모델에서는 표현이 달라질 수 있다. 모델을 바꾸면 기준 원고와 나란히 읽어 봐야 한다.
- 구운몽ST **원본**은 GPT 와 Sonnet 으로 돌린 기록이 있다. 수정본을 GPT 로 돌린 기록은 없다.
- 수필체는 Gemini 3.1 Pro · DeepSeek에서도 돌려 봤으나 형식 · 문체 오류가 있었다(§8).
- **출력 상한에는 추론 토큰이 들어간다.** 수필체 · 문학체는 본문보다 추론과 각색 기록이 훨씬 길다(문학체: 본문 약 4천 자에 출력 4만 8천 토큰). 지금 파이프라인의 장 집필 상한(6,000 토큰 · 90초)과 전체 상한(600초)으로는 돌지 않는다.
- 필요한 환경변수 이름(값은 이 자료에 없다): 실험은 `ANTHROPIC_API_KEY` · `OPENAI_API_KEY` 를 썼다. 서비스는 `GEMINI_API_KEY` 와 `MEMOIR_*` 설정을 쓴다. 문체별 모델을 가르는 설정 이름은 정해진 것이 없다.

## 8. 오류 처리 — 실험에서 실제로 본 것

| 현상 | 어디서 | 권하는 처리 |
|---|---|---|
| **출력이 상한에서 잘림** | 수필체 × Fable 5.1 | 종료 사유가 정상 완료가 아니면 **JSON이 맞아 보여도 원고로 쓰지 않는다** |
| `essay_id` 에 예시값 `e48` | 수필체 × Sonnet 5.5(3장 중 1장) · Gemini 3.1 Pro · DeepSeek | 수필체 프롬프트의 출력 예시에 그 값이 적혀 있다. **프롬프트는 고치지 않는다.** 응답의 `essay_id` 를 요청한 장과 대조하고, 다르면 형식 오류로 기록한다(본문은 온전했다). 덮어써서 통과시킬지는 결정 사항 |
| `where` 를 "…"로 이어 적음 | 수필체 × Gemini · DeepSeek | 사실 대조 실패로 둔다. 고쳐서 통과시키지 않는다 |
| 서술에 구어 존댓말이 섞임 | 수필체 × Gemini 3.1 Pro | 문체 검사로 잡는다. 그 모델은 수필체에 맞지 않았다 |
| 제목을 바꿔 냄 | 수필체(저장 결과 9개 중 4개) | 목차 제목을 쓰고 차이를 기록 |
| 각색 기록 누락 | 수필체 · 문학체 | 모델의 기록을 그대로 믿지 않는다. 본문 대조가 따로 필요하다 |
| 프롬프트 예시가 본문에 옮겨짐 | 문학체(이미지 4개) | 프롬프트는 그대로 둔다. 알려진 제약으로 기록 |
| 스키마 밖의 키 | 수필체 × Gemini(JSON 모드) | 스키마 강제(구조화 출력)를 쓴다 |
| 따옴표가 곧은 모양으로 나옴 | 소설체 수정본 × Sonnet 5.5 | 대사를 찾을 때 두 모양을 모두 본다. 본문을 바꿔 맞추지 않는다 |

**재시도 정책은 결정 사항이다.** 실험은 모두 재시도 0 · 대체 모델 없음으로 돌렸다.

## 9. 결정 사항 요약

`remaining_decisions.md` 에 담당자별로 적었다. 연동을 시작하기 전에 정해야 하는 것 — ① 문체 값의 정합 ② 문체별 모델 ③ 분석 단계를 어떻게 들일 것인가(안전 사본의 지시문을 쓸지, 서비스의 분석을 넓힐지) ④ 응답 규격을 문단 단위로 넓힐 것인가 ⑤ 소설체의 사실 확인 방법.

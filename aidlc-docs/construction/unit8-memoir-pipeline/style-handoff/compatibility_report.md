# 호환성 검토

2026-11-11 · 유료 호출 0회. **저장된 실험 결과와 코드 읽기만으로** 본 것이다. 서비스에서 실제로 돌려 본 것은 하나도 없다 — 돌려 보지 않은 호환성을 성공으로 적지 않았다.

## 1. 판정

| 문체 | 기존 백엔드 출력과의 호환 | 근거 |
|---|---|---|
| 수필체 | **추가 백엔드 구현 필요** | 출력(JSON 문단)은 변환하면 응답에 넣을 수 있다. 그러나 입력(장 자료 묶음)을 만들 분석 결과가 서비스에 없고, 모델 · 출력 상한 · 시간 상한이 지금 설정과 맞지 않는다 |
| 문학체 | **추가 백엔드 구현 필요** | 수필체와 같다. 더해서 문단 안 줄바꿈 · 조각 문장을 지키는 응답 · 저장 방식이 필요하다 |
| 소설체 | **추가 백엔드 구현 필요** | 입력은 간단하다(원문만). 그러나 출력이 JSON이 아니고 제목 · 사실 표시 · 각색 기록이 없어, 응답의 근거 턴과 검증 상태를 채울 수단이 없다 |

세 문체 가운데 "기존 백엔드 출력과 호환" 또는 "데이터 변환만으로 호환"이라고 할 수 있는 것은 없다.

## 2. 입력 구조 비교

| 입력 | 수필체 | 문학체 | 소설체 | 서비스에 지금 있는가 |
|---|---|---|---|---|
| 인터뷰 원문(장 단위) | 필요 | 필요 | 필요 | 있다(회차 · 턴) |
| 사실 원장(id · 내용 · 출처 · 확실성) | 필요 | 필요 | — | 있다(값 체계 같음 · id 모양 다름) |
| 반드시 남길 세부 | 필요 | 필요 | — | **없다** |
| 감정 기록 | 필요(집필 방향 안) | 필요 | — | **없다** |
| 지금의 회고 · 인물 · 때 · 곳 · 들은 이야기 · 직접 인용 | — | 필요 | — | 같은 모양으로는 없다 |
| 장별 집필 방향 | 필요 | — | — | **없다** |
| 장별 주의 · 다른 장과의 겹침 | 필요 | 필요 | — | **없다** |
| 목차(장별 이야기 배치) | 필요 | 필요 | — | 있다 |
| 제목(확정 · 검증 상태) | **필요** | 임시값 가능 | — | 제목은 있다. 검증 상태 표시는 없다 |
| 민감 여부 | 필요 | 필요 | — | 없다 |
| 앞 장 연결 자료 | — | — | 선택(실행 기록 없음) | 없다 |

구분:

1. **이미 공통으로 줄 수 있는 것** — 원문 · 사실 원장(값 체계) · 목차의 이야기 배치.
2. **구조 변환만으로 되는 것** — 사실 id 모양(`f12` ↔ `f41-1`), 턴 번호 → 이야기 번호, 묶음의 Markdown 조립(참조 구현 있음).
3. **백엔드 구현이 필요한 것** — 지킬 세부 · 감정 기록 · 장별 주의 · 집필 방향을 만드는 분석 호출, 확정 제목의 공급, 민감 판정, 문체별 모델 호출.
4. **아직 판단할 수 없는 것** — 서비스의 v7 분석을 넓혀 만든 묶음으로도 문체가 유지되는가 / 소설체를 여러 장으로 이어 쓸 때의 연결.

### 지금 응답 규격과 맞대 보면

지금 응답(`memoir.pipeline_result`)은 문장마다 `text` 와 `turns` 를 싣고, `body` 는 문장을 한 줄씩 이어 붙인다.

| 응답이 요구하는 것 | 수필체 | 문학체 | 소설체 |
|---|---|---|---|
| 장 제목 | 목차에서(모델 값은 쓰지 않음) | 같다 | 목차에서 |
| 문단 → 문장 | 나눌 수 있다 | 나눌 수 있으나 **조각 문장 · 문단 안 줄바꿈이 문장 분리와 부딪힐 수 있다** | 줄 · 빈 줄이 경계 |
| 문장의 근거 턴 | 사실의 자리로 일부만 채워진다 | 189문장 중 27곳만 | **채울 수 없다** |
| `body`(문장마다 줄바꿈) | 문단 경계가 사라진다 | **문체가 훼손된다** | **대사와 장면의 구분이 사라진다** |
| 검증 상태 | 사실 대조로 채울 수 있다 | 같다(문체 규칙은 따로) | 채울 수단 없음 |

각색 기록은 지금 응답에 자리가 없다. 싣는다면 수필체의 5키는 문학체 7키의 부분집합이라 한 모양으로 맞출 수 있다. 유형 이름은 두 문체가 다르므로 **원래 유형을 함께 보존**하는 것을 권한다.

## 4. 문체 매핑의 충돌

| 기본값 | `spoken`(구어체) | — | 새 문체 3종에 구어체가 없다. 기존 값을 남길지, 수필체로 바꿀지 정해야 한다 |

## 6. 실제 호출 미검증 — 확인하지 못한 것

1. 서비스의 기본 모델(Gemini 3.5 Flash Lite)로 세 문체를 돌린 결과.
2. 서비스의 v7 분석 결과로 만든 묶음으로 수필체 · 문학체를 돌린 결과.
3. 문학체를 검증한 장 이외의 원문으로 돌린 결과(한 장 · 한 번).
4. **소설체 수정본**을 다른 원문 · 다른 모델(GPT 포함)로 돌린 결과, 같은 원문으로 다시 돌렸을 때의 재현성(한 원문 · 한 번).
5. 소설체를 여러 장으로 이어 쓴 결과(`[앞 장에서 이어받을 내용]` 을 채운 실행).
6. 문체 출력을 지금 응답 규격으로 바꿔 화면에 보인 결과(줄바꿈 보존).
7. 기존 편집 · 검증 단계(4 · 5단계)를 문체 원고에 돌린 결과.
8. 세 문체를 한 책 안에서 장마다 섞어 썼을 때의 일관성.
9. 참조 구현을 서비스 코드로 옮겨 실제 요청 경로에서 돌린 결과 — 이 자료의 테스트는 파일과 형식만 본다.
10. **안전 사본의 분석 지시문으로 실제 분석을 돌린 결과** — 실험에 쓴 원본에서 예시의 이름 하나를 바꾼 사본이다. 구조와 입력 조립은 무료로 확인했으나, 모델이 원본 때와 같은 분석을 내는지는 실서비스 연동 후 검증이 필요하다.

## 7. 호환성에서 건질 것

- 사실 원장의 값 체계(self/heard/view · stated/approx/uncertain)는 서비스와 실험이 같다.
- 수필체 · 문학체의 최상위 출력 모양은 같다 — 한 조립기로 받을 수 있다.
- 수필체 출력 스키마와 사실 대조는 이미 `develop` 에 있다(`backend-agent/tools/memoir_literary.py`).
- 일감 경로(`memoir_jobs`)와 "잘린 응답은 원고가 아니다" · "고쳐서 통과시키지 않는다"는 원칙은 실험과 서비스가 같다.
- `style` 값이 요청 → 응답으로 이미 흐르고 있어, 분기할 자리가 분명하다.
- 소설체는 분석 단계 없이 원문만으로 돈다 — 세 문체 가운데 입력 쪽 연결이 가장 가볍다.

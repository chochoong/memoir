## 화면 정책과 서버 메타데이터

| 구분 | 값·동작 |
| --- | --- |
| 정적 `reviewPolicy` | `{min:3,max:null}`. 이 화면에서 6장 이상을 선택하고 예시 본문을 모을 수 있으며 요청은 보내지 않습니다. |
| 기존 프론트 `legacyPolicy` | `{min:3,max:5}`. 기존 프론트 기준과 잘못된 정책 입력의 복구값입니다. 모든 서버·엔진에 적용되는 고정 상한을 뜻하지 않습니다. |
| 서버 최소·최대 | `MIN_SESSIONS=3`. 명시 선택 최대는 `MEMOIR_MAX_SESSIONS` 환경 값이며 코드 기본값은 5입니다. |
| 기존 limits 응답 | `GET /api/sessions?elder_id=...`가 `memoir_engine`, `memoir_max`, `memoir_max_chars`, `memoir_enabled`, `memoir_total`을 이미 반환합니다. `elder_id`가 없는 목록 응답에는 이 메타가 없습니다. |
| 계정별 차이 | 엔진·허용 계정·기능 개방은 서버 설정을 따릅니다. `memoir_max:null`은 pipeline의 전체 제외 요청에 개수 상한이 없음을 나타내며, 명시 선택 검사를 우회하는 신호로 해석하면 안 됩니다. |

**이번 작업에서 서버 상한을 해제하거나 새 capability API를 만든 것이 아닙니다.** 실제 연결은 기존 메타데이터와 요청 모드를 사용합니다. 최소값은 현재 서버 상수 3을 따르되 향후 제품 정책 변경 시 양쪽을 맞춥니다. `memoir_enabled:false`와 메타 조회 실패를 정상 개방 상태로 처리하지 않도록 화면 동작을 합의합니다.

## 직접 고르기와 전체에서 제외하기

동기 `POST /api/memoirs/preview`와 비동기 `POST /api/memoirs`는 이미 두 요청 모드를 받습니다.

| 요청 모드 | 현재 서버 동작 |
| --- | --- |
| `{"session_ids":[...]}` | 명시적으로 고른 UUID 배열. `check_selection()`에서 최소 3과 환경 최대값을 검사합니다. **pipeline 계정도 이 요청 모드에는 같은 최대값 검사가 적용됩니다.** |
| `{"elder_id":"...","exclude_session_ids":[...]}` | 해당 계정·화자의 자서전 대상 전체에서 제외 목록을 뺍니다. 남은 회차는 최소 3개여야 하며, `single`은 환경 최대값을 적용하고 `pipeline`은 개수 상한을 적용하지 않습니다. 본문 길이 등 별도 검사는 유지됩니다. |

전체 제외의 기준은 같은 계정·화자의 **닫힌·말씀 있는 회차 전체**입니다. 엽서가 있는 회차만으로 한정되지 않습니다. `elder_id`의 소유권과 회차별 소유권·화자 혼합·화자 미지정·입력 길이 검사는 이미 서버에 있습니다. 가상 로그인에서 고른 이름을 실제 `elder_id`로 보내지 않습니다.

현재 시안은 `state.previewRequest.session_ids`를 클릭한 순서대로 구성합니다. UUID 필드와 배열 순서는 유지하며, 선택 취소 후 다시 고르면 배열의 마지막에 둡니다. 이 객체와 목업 초안은 서버에 전송하지 않습니다.

```json
{
  "session_ids": [
    "00000000-0000-4000-8000-000000000003",
    "00000000-0000-4000-8000-000000000001",
    "00000000-0000-4000-8000-000000000002"
  ]
}
```

위 값은 가상 UUID입니다. 실제 생성 순서는 이 클릭 순서와 구분해야 합니다. `collect()`는 요청 배열 순서로 읽지만 `merge()`는 `created_at` 순서로 정렬하며 single·pipeline 모두 이를 사용합니다. 전체 제외 요청도 서버의 `store.memoir_sessions()`가 회차를 연 순서로 집계합니다. 이는 인생 사건의 연도순을 뜻하지 않습니다. **직접 고른 순서를 편집 순서로 약속할지, 서버의 기록 순서를 사용할지**를 실제 연결 전에 합의하고 화면 설명을 맞춥니다.

## 목록 20개와 전체 집계

원본 프론트 `CONFIG.memoir.listLimit`는 20이고 기존 목록 API의 limit 상한은 100입니다. 화자별 목록은 이 범위까지만 보여 주지만 `memoir_total`은 해당 화자의 자서전 대상 전체 수를 반환합니다. 전체 제외 모드는 보이는 목록 20개를 넘는 회차도 서버에서 집계합니다.

따라서 전체 생성에 모든 UUID를 프론트로 내려받는 절차를 새로 요구하지 않습니다. 별도 UI 과제는 **목록에 보이지 않지만 포함되는 오래된 기록을 사용자가 확인하고 제외할 방법**입니다. 전체 대상 수와 보이는 수의 차이를 안내하고, 실제 요구에 따라 추가 조회·페이지네이션·검색 등 탐색 방식을 합의합니다. 단순 limit 증가는 전체 조회와 같지 않으며, 아직 없는 cursor 지원을 전제하지 않습니다. 직접 선택 모드라면 페이지를 바꿔도 선택 UUID와 클릭 순서를 유지해야 합니다.

## 기존 비동기 생성·오류 계약 활용

`POST /api/memoirs`는 선택·자료 검사를 먼저 수행하고 통과하면 `202 {job_id,status:"running",...}`을 반환합니다. `GET /api/memoirs/{job_id}`로 running·done·failed와 진행 단계를 조회하고, `GET /api/memoirs/latest`로 최근 작업을 찾으며, `DELETE /api/memoirs/{job_id}`로 취소합니다. 실행 중이면 새 작업 대신 `409 {code:"busy",job_id}`를 반환합니다. **새 비동기 API나 queue를 추가해야만 연결할 수 있는 상태가 아닙니다.**

연결할 때 확인할 것은 기존 기능을 화면에 맞추는 일입니다.

- `memoir_max_chars`와 실제 `MEMOIR_MAX_INPUT_CHARS`, 엔진·계정별 허용값을 확인합니다. 요청 본문은 기존 `_memoir_body()`의 64KB 제한도 받습니다. 개수 상한이 없더라도 입력 길이는 무제한이 아닙니다.
- 기존 작업 조회 간격·진행 단계·완료 화면, `409 busy`에서 기존 작업 이어보기, 취소, 새로고침 복구를 연결합니다. 작업 보관 기간·서버 재시작 후 `job_not_found`와 배포 timeout은 운영 환경에서 확인합니다.
- 자료 부족, 잘못된 선택, 화자 혼합·미지정, `too_much`, 자료 조회 실패, 모델 실패·timeout, 취소를 기존 status·code로 구분합니다. 지금의 정적 지연 표시는 실제 처리 시간이나 오류 동작의 검증 결과가 아닙니다.

## 현재 프론트에 반영한 화면

- 인터뷰 완료에서 엽서를 자동 추가하지 않습니다. 제출 답변과 작성 중인 글을 별도의 탭 메모리 이야기로 복사하고 원문을 확인한 뒤 「예시 엽서 만들기」를 눌러야 엽서 목록·자서전 선택에 추가됩니다. 나중에 만들기는 기존 엽서보기 안의 접힌 영역에서 재조회합니다. 빈 완료·중복 클릭을 막고 원문의 공백·줄바꿈을 보존합니다. 이는 정적 화면의 동선 보강이며 실제 마지막 발화 확정·업로드·DB 저장 대기·서버 기록 조회·실패 처리는 기존 API에 연결할 때 구현해야 합니다.
- 엽서는 기본적으로 본문 조회입니다. 「자서전 만들기」를 누른 뒤 선택 모드로 들어가고, 상단 설명 아래의 화살표가 있는 높이 48px outline 「엽서 보기로 돌아가기」 버튼으로 복귀합니다.
- 선택 → 문체 예시 → 초안 수정 → 작은 책 보관 → 자서전 목록의 흐름입니다. 책장은 모아둔 얇은 책의 목록·열기만 제공하며 생성·합본 동작을 넣지 않았습니다.
- PC·모바일은 같은 리더를 사용합니다. `slide` 기본과 `scroll`을 지원하며 글자 18~32px·줄 간격 1.6~2.3을 조절합니다. 폭 1100px 이상·높이 560px 이상인 PC 페이지 보기는 좌우 두 면, 좁은 PC·모바일은 한 면입니다.
- `paper`는 PC 좌우 두 면이 보일 때만 보기 설정에서 선택합니다. 앞·뒷면이 있는 한 장을 420ms 동안 180도 넘기는 효과이며, 단면 화면에서는 옵션을 숨깁니다. 저장된 PC용 `paper` 선호는 유지하되 단면의 유효 동작은 `slide`이고 `aria-pressed` 선택 표시도 이에 맞춥니다.
- 종이책·옆넘김 효과는 직접 책장을 넘길 때만 표시합니다. 사용자 움직임 줄이기 또는 OS 설정이 켜져 있으면 효과를 끕니다. 목차·책갈피 이동, 설정·크기 변경에는 넘김 효과를 붙이지 않습니다. 화면 높이 560px 미만 또는 폭 260px 미만에서는 스크롤로 전환합니다.
- 페이지 재배치 시 문단·글자 위치 비율로 읽던 대목을 복원하며 오른쪽 페이지의 대상 위치도 보존합니다. `sameView()`는 표지를 포함한 현재 펼친 면 기준으로 양쪽 책갈피를 판정하고, 저장된 개별 위치는 합치지 않습니다. 마지막 펼친 면의 진행률은 100%이며 실제 끝을 넘는 쪽수·다음 이동을 만들지 않습니다.
- localStorage에는 보기 설정, 내용 구분용 해시와 숫자 위치·책갈피 등만 저장합니다. 진행도 키는 `naemalssami.ui-review.reader.progress.v2.`이며 실제 자서전 제목·본문·인터뷰 답변은 저장하지 않습니다. 새로 보관한 책은 현재 탭 메모리에만 있습니다.
- 아바타에서 `Google Login Mock Data` 버튼 한 번으로 고정 예시 계정에 들어가는 정적 대화상자를 엽니다. 예시 화자는 `나`이며 중간 선택을 생략합니다. 실제 인증·첫 화자 등록은 연결하지 않았으며 원본 로그인 조사·세션 연결 의제는 [로그인 전달서](LOGIN_HANDOFF.md)에서 별도로 관리합니다.

책장의 나무 선반과 표지 표현은 팀 원본 `prototype/book.html`의 `.sh-plank` 861~866행·`.sh-cover` 870~879행에서 재사용했습니다. 출처 커밋은 `088b23f40efce837909cdc54faa388fa2c2016fb`, blob은 `6666df60a5ab273814d37d8dff626f8ba488c1b9`이며 상세 링크와 라디오 출처는 [README](README.md)에 있습니다.

## 향후 별도 의제

실제 책 저장·목록·다시 열기와 기기 간 읽기 위치 동기화는 별도 API와 보관 정책이 필요합니다. 얇은 책 여러 권을 합치는 합본은 순서·중복 처리·편집·생성 비용을 합의한 후 다룰 향후 기능입니다. 현재 시안에는 합본 구성·생성, PDF·인쇄가 연결되어 있지 않습니다.

브라우저 확인 결과와 실제 연결 후 검증 결과는 구분해 기록합니다. 이번 정적 화면 검토가 서버 상한 변경이나 서비스 반영·병합 승인을 의미하지 않습니다.

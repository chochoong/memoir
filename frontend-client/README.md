# frontend-client — 기억의 조각 화면

React + TypeScript + Vite. 1주차는 **인터뷰 흐름 시험 화면** 하나다.

```powershell
npm install
copy .env.example .env.local     # VITE_API_BASE 확인
npm run dev
```

`http://localhost:5173` — 백엔드가 8010에서 돌고 있어야 한다.

---

## 구조

```
src/
  main.tsx        진입점
  App.tsx         화면 전체 (1주차는 한 장)
  api.ts          백엔드 호출 · 타입 정의
  recorder.ts     마이크 · 무음 판정 · 16kHz PCM
  speaker.ts      낭독 재생 · iOS 잠금 해제
  log.ts          화면에 찍는 기록 (리액트 밖)
  LogPanel.tsx    ⑥ 검은 창
  styles.css      어르신 기준 (24px 본문 · 64px 터치 · 360px 폭)
```

**백엔드 호출은 전부 `api.ts`를 지난다.** 컴포넌트가 `fetch`를 직접 부르기 시작하면 주소와 헤더가 흩어져 수습이 안 된다. `X-User-Id` 헤더도 여기 한 곳에 있으니, 구글 로그인이 붙으면 이 파일만 고치면 된다.

---

## 이미 지켜 둔 것

1주차 시험 화면이지만 어르신 기준을 처음부터 넣어 두었다. 나중에 다시 고치는 것보다 싸다.

| | 값 | 근거 |
|---|---|---|
| 본문 글자 | 18px, 질문은 24px | NFR-AC-001 |
| 버튼 높이 | 64px 이상 | NFR-AC-002 |
| 기준 폭 | 360px에서 깨지지 않음 | NFR-EN-001 |
| 오류 표시 | 빈 화면으로 멈추지 않고 문구를 띄운다 | 원칙 3 |

409(정의되지 않은 상태 전이)가 오면 화면 상단에 그대로 드러난다. 개발 중에 상태 머신이 어긋나는 걸 바로 알아채려는 것이다.

---

## 상태는 폴링으로 갱신한다

서버가 **타이머로** 상태를 바꾸기 때문에, 버튼을 누를 때만 갱신하면 T1·T2가 만료되는 걸 화면이 모른다. 그래서 300ms마다 물어본다.

```ts
const POLL_MS = 300
```

4일차에 WebSocket으로 교체하면 `App.tsx`의 폴링 훅 하나만 갈아 끼우면 된다. `api.ts`와 화면은 손대지 않는다.

---

## 개발은 localhost로 한다

**터널(https)을 상시로 켜두지 않는다.** 브라우저는 `http://localhost`를 secure context로 취급하므로, 마이크 권한도 구글 로그인도 서비스워커도 **본인 컴퓨터에서는 그냥 된다.**

터널로 상시 개발하면 HMR WebSocket이 릴레이를 지나 핫리로드가 느려지고, Vite가 모르는 호스트를 막아서 별도 설정도 필요해진다. 화면 작업 속도만 잃는다.

## 실기기 확인

### 같은 wifi에서 화면만 보기

`vite.config.ts`에 `host: true`가 이미 들어 있다. `npm run dev` 하면 터미널에 LAN 주소가 찍히고 폰에서 접속된다.

다만 **http라서 마이크 권한이 안 뜬다.** 레이아웃만 볼 때 쓴다.

### https로 마이크까지 확인하기

```powershell
npm run deploy:backend        # 빌드 → ../backend-agent/web 으로 복사
```

그다음 backend-agent 쪽에서 uvicorn을 띄우고 Tailscale Funnel을 건다. 자세한 건 backend-agent의 README 참조.

**프론트와 API가 같은 출처라 CORS도 HMR 설정도 필요 없다.** `.env.local`의 `VITE_API_BASE`는 비워 둔다.

코드를 고칠 때마다 다시 빌드해야 하므로, **화면을 다듬는 작업은 localhost에서 하고 다 됐을 때 빌드해서 폰으로 확인하는** 리듬이 맞다.

### 굳이 Vite 개발 서버를 터널로 열어야 한다면

Vite가 모르는 호스트 이름을 기본으로 막는다. `Blocked request`가 뜨면 이걸 추가한다.

```ts
// vite.config.ts
server: {
  host: true,
  port: 5173,
  allowedHosts: ['.ts.net'],
  hmr: { protocol: 'wss', clientPort: 443 },
}
```

다만 터널을 두 개(프론트 5173, 백엔드 8010) 열어야 하는데 Funnel은 공개 포트가 443/8443/10000뿐이라 번거롭다. 위의 빌드 방식을 권한다.

## 마이크 (`recorder.ts`)

**소리가 있는 구간만 올린다.** 무음까지 올리면 서버의 T1 이 영원히 리셋되어 발화가
확정되지 않는다 — 대화가 멈춘다. 이 파일이 틀리면 그렇게 된다.

판정을 화면에 둔 이유는 서버에 이미 T1 이 있기 때문이다. T1 은 「무음 3초」의
정의이고, **아무것도 보내지 않는 것이 곧 무음 신호다.** 서버에서 또 판정하면 둘이
어긋날 때 원인을 찾을 수 없다.

`tools/replay.py` 의 `_voiced()` 가 초안이었다. 거기엔 없던 둘을 더했다.

| | 왜 |
|---|---|
| 잡음 바닥 추정 | 조용한 방과 시끄러운 방에서 같은 임계값은 못 쓴다 |
| 이력(hysteresis) | 임계값 하나면 경계에서 켜졌다 꺼졌다 하며 말을 썬다 |
| 말머리 300ms | 판정이 열리기 전 소리를 함께 보낸다. 없으면 「어」가 잘린다 |
| 1초마다 올림 | 말이 길어도 T1 이 계속 밀려야 한다 |

바닥은 **조용할 때만** 다시 잰다. 말하는 동안 올리면 바닥이 목소리를 따라 올라가
문장 뒤쪽이 통째로 무음으로 판정된다.

낭독 중이나 정리 중에 들어온 소리는 버린다. 스피커에서 나온 질문이 그대로 되돌아와
T1 을 리셋하면 발화가 영영 확정되지 않는다.

### MediaRecorder 를 쓰지 않는다

잘라낸 webm 조각은 이어 붙지 않는다 — 헤더가 여럿이 되어 디코더가 첫 조각까지만
읽고, 어르신의 뒷말이 사라진다. 머리 없는 PCM 은 그냥 이어 붙는다. 자세한 것은
`backend-agent/README.md` 의 「왜 webm 이 아니라 머리 없는 PCM 인가」.

`ScriptProcessorNode` 는 폐기 예정이지만 iOS 사파리를 포함해 어디서나 돈다.
`AudioWorklet` 으로 옮기는 것은 별도 모듈 파일이 필요해 미뤘다.

### https 가 아니면 마이크가 없다

`navigator.mediaDevices` 는 보안 컨텍스트에서만 존재한다. 사파리는 「거부」가 아니라
`undefined` 라서 권한 오류가 아니라 **기능 없음**으로 터진다. `recorder.ts` 가 그
경우를 따로 잡아 「https 가 필요합니다」로 말한다.

## 낭독 (`speaker.ts`)

질문이 나오면 서버에서 mp3 를 받아 틀고, **끝까지 튼 뒤에 `tts-done` 을 올린다.**
낭독이 끝나는 시각은 서버가 알 수 없다. 여기서 올려야 T1 이 정확한 순간부터
돈다 — 몇백 밀리초 어긋나면 「무음 3초」가 무음 2.6초가 된다.

### iOS 는 사용자 동작 없이 소리를 안 낸다

회차를 여는 탭(`run()`)에서 무음 wav 를 아주 잠깐 틀어 잠금을 푼다.
**요소를 매번 새로 만들면 잠금이 풀리지 않으므로 `<audio>` 하나를 끝까지
돌려쓴다.** 이걸 모르고 `new Audio(url).play()` 를 쓰면 폰에서만 조용히 실패한다.

### 소리가 없어도 회차는 간다

서버가 204 를 주면 소리가 없다는 뜻이지 실패가 아니다. 글자는 그대로 띄우고
「낭독 끝」 버튼으로 넘어간다. 재생이 거부돼도 같다 — 문구만 바꾸고 버튼을 남긴다.
**소리가 안 나는 것과 회차가 끊긴 것은 어르신에게 전혀 다른 일이다.**

### 낭독 중에는 마이크 판정을 끈다

`recorder.setActive(false)`. 안 끄면 스피커에서 나온 질문이 마이크로 되돌아와
판정이 열린 채로 남고, 수음이 열리는 순간 그 꼬리가 어르신의 첫마디인 양 올라간다.
업로드 쪽에도 같은 조건이 걸려 있다 — 두 겹이다.

## 기록 (`log.ts` · `LogPanel.tsx`)

**폰에는 열어 볼 콘솔이 없다.** 개발은 노트북에서 하지만 실제 시험은 폰에서
하는데, 거기서는 마이크가 언제 올라갔는지 · 상태가 언제 넘어갔는지 · 무엇이
터졌는지 볼 데가 없다. 화면 맨 아래 검은 창 하나가 그 자리다.

### 리액트 밖에 둔다

`log.ts` 는 훅이 아니라 모듈이다. **오디오 콜백과 `fetch` 안에서도 불러야
하기 때문**이다. 훅으로 만들면 정작 찍고 싶은 자리에서 못 부른다. 화면은
`useSyncExternalStore` 로 붙어 보기만 한다.

목록을 고칠 때 배열을 **갈아 끼운다.** `push` 로 밀어 넣으면 참조가 그대로라
화면이 영영 안 바뀐다. 300줄까지만 들고 오래된 것부터 버린다 — 폰 메모리다.

### 무엇을 찍나

| 태그 | 언제 |
|---|---|
| `회차` `상태` `턴` | 스냅샷이 **바뀔 때만**. 폴링이 300ms 마다 같은 값을 물어온다 |
| `조각` | 전사 결과. 마이크를 시험할 때 가장 보고 싶은 한 줄이다 |
| `질문` | 새 질문이 왔을 때 |
| `마이크` `올림` | 켬/끔, 청크가 올라간 길이. 올림은 흔한 일이라 흐리게 |
| `소리` `낭독` | mp3 크기와 받는 데 걸린 시간, 읽은 시간 |
| `요청` `창` | 실패한 호출, 그리고 **리액트 밖에서 터진 것** |

마지막 줄이 중요하다. `window` 의 `error` · `unhandledrejection` 을 걸어 두지
않으면 **폰에서만 나는 오류가 조용히 사라진다.**

### 바닥에 붙되 붙잡지는 않는다

새 줄이 올 때마다 무조건 끌어내리면 방금 지나간 오류를 읽을 수가 없다.
바닥 근처(40px)에 있을 때만 따라 내려간다.

## 남은 일 (승우님)

1주차 화면은 **개발자용 시험 도구**다. 어르신이 볼 화면은 아니다.

2주차부터 만들 실제 화면은 요구분석서 7.1의 목록을 따른다.

| 코드 | 화면 |
|---|---|
| LG | 로그인 |
| PF | 프로필 입력 |
| ST | 이야기 시작 (사진 등록 · 제목) |
| IV | 인터뷰 |
| ED | 문장 수정 |
| PC | 엽서 만들기 |
| AR | 보관함 |

`styles.css`의 토큰(`--accent`, `--rule` 등)과 버튼·입력 스타일은 그대로 가져다 쓰면 된다. IV 화면은 지금 `App.tsx`의 구조를 크게 바꾸지 않아도 된다 — 버튼 문구와 배치만 어르신용으로 다듬으면 된다.

PWA(홈 화면 설치)를 넣기로 하면 `manifest.json`·아이콘·서비스워커가 여기 들어온다. 팀에서 결정한 뒤 착수한다.
